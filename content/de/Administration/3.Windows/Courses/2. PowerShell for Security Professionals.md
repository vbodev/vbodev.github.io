## 1. Schnellstart

### Was PowerShell ist

PowerShell verbindet eine Befehlszeile mit einer Skriptsprache. Befehle geben üblicherweise keine einfachen Texte, sondern .NET-Objekte zurück. Dadurch können Objekte durch die Pipeline weitergereicht und ihre Eigenschaften ohne manuelles Parsen von Zeichenfolgen angesprochen werden.

Vollständige Cmdlet-Namen folgen dem Muster Verb-Noun:

~~~powershell
Get-Process
Get-Service
Set-ExecutionPolicy
Invoke-RestMethod
~~~

Der korrekte Begriff lautet **Cmdlet**. Windows PowerShell 5.1 ist in aktuellen Windows-Versionen integriert; PowerShell 7 ist ein separates plattformübergreifendes Produkt, das bei Bedarf zusätzlich installiert wird.

### Einen PowerShell-Befehl lesen

Diese Zeile lässt sich in folgende Teile zerlegen:

~~~powershell
Get-Process -Name 'powershell' -ErrorAction SilentlyContinue
~~~

- `Get-Process` ist der Cmdlet-Name: Das Verb `Get` bedeutet abrufen, `Process` ist das Substantiv.
- `-Name` ist ein benannter Parameter.
- `'powershell'` ist der Wert des Parameters Name.
- `-ErrorAction` ist ein allgemeiner Parameter, der das Verhalten bei einem nicht terminierenden Fehler steuert.
- `SilentlyContinue` ist der Wert von ErrorAction: Fehler nicht anzeigen und fortfahren. Verwenden Sie dies in echten Skripten nicht ohne Grund.

Syntax und Parametersätze ermitteln:

~~~powershell
Get-Command Get-Process -Syntax
Get-Help Get-Process -Parameter Name
Get-Help about_CommonParameters
~~~

Benannte Parameter sind besser. Eine positionale Schreibweise ist kürzer, aber weniger eindeutig:

~~~powershell
Get-Process -Name 'powershell'  # eindeutig
Get-Process 'powershell'        # funktioniert positional, ist aber weniger explizit
~~~

Ein Switch-Parameter ist ein Schalter ohne separaten Wert:

~~~powershell
Get-ChildItem -Recurse -Force
~~~

Hier aktiviert `-Recurse` die Durchsuchung von Unterordnern, während `-Force` versteckte Elemente anzeigt.

### Wichtige Syntaxzeichen

| Schreibweise | Bedeutung |
|---|---|
| `$name` | Variable |
| `-Name` | Befehlsparameter |
| `'text'` | Zeichenfolge ohne Variablenersetzung |
| `"text $name"` | Zeichenfolge mit Variablenersetzung |
| `$(...)` | Ausdruck innerhalb einer Zeichenfolge oder eines anderen Ausdrucks auswerten |
| `(...)` | Ausdruck gruppieren oder zuerst ein Befehlsergebnis abrufen |
| `{...}` | Codeblock: Rumpf einer Funktion, Schleife, Bedingung oder eines ScriptBlocks |
| `@()` | Immer ein Array erstellen |
| `@{ Key = Value }` | Hashtable mit Schlüssel/Wert-Paaren erstellen |
| `[type]` | Typ angeben oder prüfen |
| `.Property` | Auf eine Objekteigenschaft zugreifen |
| `.Method()` | Eine Methode aufrufen |
| `\|` | Objekte an den nächsten Befehl übergeben |
| `&` | Aufrufoperator: Befehl/Skript ausführen, dessen Pfad ein Ausdruck ist |
| `#` | Einzeiliger Kommentar |
| `<# ... #>` | Mehrzeiliger Kommentar oder kommentarbasierte Hilfe |

Beispiel mit mehreren Konstrukten:

~~~powershell
$serviceName = 'WinRM'
$service = Get-Service -Name $serviceName

if ($service.Status -eq 'Running') {
    "Service $($service.Name) is running"
}
~~~

Der Punkt in `$service.Status` greift auf die Eigenschaft Status zu. `$($service.Name)` wertet innerhalb einer Zeichenfolge mit doppelten Anführungszeichen einen komplexeren Ausdruck als eine einfache Variable aus.

### Variablen und Datentypen

Eine Variable wird durch Zuweisung erstellt:

~~~powershell
$name = 'server01'
$count = 3
$enabled = $true
$checkedAt = Get-Date
~~~

Typen prüfen:

~~~powershell
$name.GetType().FullName
$count.GetType().FullName
$checkedAt.GetType().FullName
~~~

Typen können explizit angegeben werden:

~~~powershell
[string]$computerName = 'server01'
[int]$retryCount = 3
[bool]$enabled = $true
[datetime]$deadline = '2026-08-20'
~~~

Häufige Typen sind `[string]` (Text), `[int]` (Ganzzahl), `[double]` (Dezimalzahl), `[bool]` (boolescher Wert), `[datetime]` (Datum und Uhrzeit), `[array]`/`[object[]]` (geordnete Sammlung), `[hashtable]` (Schlüssel/Wert-Paare) und `[pscustomobject]` (Objekt mit benannten Eigenschaften).

PowerShell konvertiert Typen oft automatisch, verlassen Sie sich aber nicht auf mehrdeutige Konvertierungen:

~~~powershell
'10' + '2'        # '102': Zeichenfolgenverkettung
[int]'10' + 2     # 12: numerische Addition
~~~

### Zeichenfolgen, Arrays, Hashtables und PSCustomObject

Einfache Anführungszeichen bewahren wörtlichen Text. Doppelte Anführungszeichen ersetzen Variablen und Teilausdrücke:

~~~powershell
$name = 'server01'

'Computer: $name'             # Computer: $name
"Computer: $name"             # Computer: server01
"Length: $($name.Length)"     # Length: 8
~~~

Ein Array, einschließlich Bereichsoperator und garantiertem Array-Ausdruck:

~~~powershell
$computers = 'server01', 'server02', 'server03'
$computers[0]
$computers[-1]
$computers.Count
$computers += 'server04'

foreach ($computer in $computers) {
    $computer
}

1..5
5..1

$services = @(Get-Service -Name 'WinRM')
$services.Count
~~~

Eine Hashtable ist für Einstellungen und Befehlsparameter nützlich. Die Übergabe an einen Befehl mit `@settings` heißt **Splatting**: Die Schlüssel werden zu Parameternamen und die Werte zu Argumenten.

~~~powershell
$settings = @{
    ComputerName = 'server01'
    Count        = 1
    Quiet        = $true
}

$settings['ComputerName']
$settings.ComputerName
Test-Connection @settings

$result = [pscustomobject]@{
    ComputerName = 'server01'
    Online       = $true
    CheckedAt    = Get-Date
}

$result.Online
$result | Format-List
$result | Export-Csv .\result.csv -NoTypeInformation
~~~

`$null` bedeutet, dass ein Wert fehlt. Setzen Sie `$null` links von einem Vergleich, damit ein Vergleich mit einer Sammlung eindeutig bleibt:

~~~powershell
$value = $null

if ($null -eq $value) {
    'Value is absent'
}
~~~

### Befehle finden, navigieren und die Objektpipeline verwenden

Aliases sind interaktiv praktisch, in gespeicherten Skripten sollten jedoch vollständige Cmdlet-Namen verwendet werden: `Get-ChildItem` statt `ls`, `Get-Location` statt `pwd`. Das macht Code leichter lesbar und übertragbar.

~~~powershell
Get-Command -Noun Process
Get-Command -Name '*Service*'
Get-Help Get-Process -Examples
Get-Alias
Get-Alias pwd
Get-Alias ls

Get-Location
Get-ChildItem
Set-Location C:\Users
Set-Location ..
Clear-Host
~~~

Die Pipeline übergibt Ergebnisse als Objekte von einem Befehl an den nächsten:

~~~powershell
Get-Process |
    Where-Object CPU -GT 10 |
    Sort-Object CPU -Descending |
    Select-Object -First 10 Name, Id, CPU
~~~

Prüfen Sie Typ und Eigenschaften eines Objekts, bevor Sie es weiterverarbeiten:

~~~powershell
Get-Process | Get-Member
Get-Service | Select-Object -First 5 | Format-Table Name, Status, StartType
~~~

`Format-Table` und `Format-List` dienen der Enddarstellung; setzen Sie sie nicht in die Mitte einer Pipeline, die Objekte noch weiterverarbeiten soll.

`foreach ($item in $items)` ist ein Sprachkonstrukt und verwendet üblicherweise eine bereits im Speicher befindliche Sammlung. `ForEach-Object { ... }` ist ein Pipeline-Cmdlet, das eingehende Objekte bei ihrem Eintreffen verarbeitet. Pipeline-Bindung kann **ByValue** erfolgen, wenn der Objekttyp zu einem Parameter passt, oder **ByPropertyName**, wenn ein Eigenschaftsname zu einem Parameternamen passt.

~~~powershell
Get-Help Stop-Service -Full

[pscustomobject]@{ Name = 'Spooler' } |
    Stop-Service -WhatIf
~~~

Hier wird die Eigenschaft `Name` an den Parameter `-Name` gebunden. Korrekte Eigenschaftsnamen sind daher bei PowerShell-Objekten wichtig.

## 2. Vorhandene Skripte lesen

PowerShell-Skripte haben die Erweiterung `.ps1`. Beim Prüfen fremden Codes ist ein Vorgehen von oben nach unten sinnvoll:

1. Hilfe-Kommentare lesen: `.SYNOPSIS`, `.DESCRIPTION`, `.PARAMETER` und `.EXAMPLE`.
2. `param(...)` finden und Eingaben sowie Pflichtparameter verstehen.
3. Variablen auflisten; sie beginnen mit `$`.
4. Funktionen, Schleifen, Bedingungen und Punkte der Remoteausführung finden.
5. Für unbekannte Befehle `Get-Help` und `Get-Command` verwenden.
6. Externe Adressen, Dateien, Module, Berechtigungen und mögliche Nebenwirkungen prüfen.
7. Statische Analyse ausführen und ohne Administratorrechte in einer isolierten Umgebung testen.

Minimal dokumentiertes Skript:

~~~powershell
<#
.SYNOPSIS
Tests availability of hosts from a text file.

.PARAMETER Path
Path to a file containing one name or IP address per line.

.EXAMPLE
.\Test-Hosts.ps1 -Path .\hosts.txt
#>

[CmdletBinding()]
param(
    [Parameter(Mandatory)]
    [ValidateScript({ Test-Path -LiteralPath $_ -PathType Leaf })]
    [string]$Path
)

$computers = Get-Content -LiteralPath $Path

foreach ($computer in $computers) {
    $online = Test-Connection -ComputerName $computer -Count 1 -Quiet

    [pscustomobject]@{
        ComputerName = $computer
        Online       = $online
        CheckedAt    = Get-Date
    }
}
~~~

Verwenden Sie `Write-Verbose` für Diagnosemeldungen in einem Advanced Script/einer Advanced Function; Benutzer aktivieren sie mit `-Verbose`. Geben Sie für Daten Objekte zurück, statt Zeichenfolgen mit `Write-Host` auszugeben.

## 3. Funktionen

Funktionen machen Code wiederverwendbar. Ein minimales Beispiel:

~~~powershell
function Show-PowerShellInfo {
    $PSVersionTable.PSVersion
    Get-Location
}

Show-PowerShellInfo
~~~

Praktische Advanced Function:

~~~powershell
function Test-HostOnline {
    [CmdletBinding()]
    param(
        [Parameter(Mandatory, ValueFromPipeline)]
        [ValidateNotNullOrEmpty()]
        [string[]]$ComputerName
    )

    process {
        foreach ($computer in $ComputerName) {
            [pscustomobject]@{
                ComputerName = $computer
                Online       = Test-Connection -ComputerName $computer -Count 1 -Quiet
            }
        }
    }
}

'server01', 'server02' | Test-HostOnline
~~~

`[CmdletBinding()]` fügt allgemeine Parameter wie `-Verbose`, `-Debug` und `-ErrorAction` hinzu; `param(...)` bildet den Funktionsvertrag; `[string[]]` akzeptiert eine oder mehrere Zeichenfolgen; `ValueFromPipeline` erlaubt Eingaben über `|`; `process` verarbeitet eingehende Pipeline-Elemente; und `[pscustomobject]` gibt strukturierte Ergebnisse zurück.

Eingaben können mit Attributen wie `[ValidateNotNullOrEmpty()]`, `[ValidateRange(1, 10)]` und `[ValidateSet('Info', 'Warning', 'Error')]` geprüft werden. Eine Funktion gibt alle normalen Success-Outputs zurück, nicht nur einen Wert nach `return`. Mit `return` wird die aktuelle Funktion bzw. der Skriptblock beendet. Geben Sie Objekte direkt oder mit `Write-Output` zurück; `Write-Host` ist für UI-Meldungen und `Write-Verbose` für Diagnosen vorgesehen.

Benennen Sie Funktionen nach `ApprovedVerb-Noun` (`Get-Verb` listet bestätigte Verben), deklarieren und typisieren Sie Parameter, geben Sie Objekte statt formatiertem Text zurück und verlangen Sie keine Administratorrechte, wenn sie nicht nötig sind.

### Eine `.ps1` ausführen

~~~powershell
# Aus dem aktuellen Verzeichnis
.\Hello-Friends.ps1

# Vollständiger Pfad; & wird benötigt, wenn der Pfad in einer Zeichenfolge steht
& 'C:\Users\User\Downloads\Hello Friends.ps1'

# Parameter übergeben
& 'C:\Scripts\Test-Hosts.ps1' -Path 'C:\Data\hosts.txt'
~~~

## 4. Execution Policy und sichere Ausführung

Policy nach Scope prüfen:

~~~powershell
Get-ExecutionPolicy -List
~~~

PowerShell-Policies heißen `AllSigned`, `RemoteSigned`, `Restricted`, `Unrestricted`, `Bypass`, `Undefined` und `Default`. Die Scope-Priorität lautet `MachinePolicy`, `UserPolicy`, `Process`, `CurrentUser`, dann `LocalMachine`; Group Policy kann lokale Einstellungen überschreiben.

Auf einem Lerncomputer ist es sicherer, nur die Policy des aktuellen Benutzers zu ändern:

~~~powershell
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
~~~

Für eine vertrauenswürdige heruntergeladene Datei:

~~~powershell
Get-FileHash .\TrustedScript.ps1 -Algorithm SHA256
Unblock-File .\TrustedScript.ps1
~~~

Die Execution Policy schützt vor versehentlicher Ausführung, nicht vor einem entschlossenen Angreifer. Ändern Sie `LocalMachine` nicht, wenn `CurrentUser` oder `Process` ausreicht; verwenden Sie `Bypass` nicht dauerhaft; prüfen Sie Code, Quelle und Hash vor der Ausführung ohne erhöhte Rechte; und nutzen Sie für nicht vertrauenswürdigen Code eine kurzlebige VM oder Windows Sandbox.

## 5. Git und Versionskontrolle

Git speichert die Änderungshistorie; GitHub ist ein Dienst zum Hosten von Git-Repositories und für Zusammenarbeit.

~~~text
working directory → staging area → local commit → remote repository
      git add          git commit         git push
~~~

Das Working Directory enthält bearbeitete Dateien; die Staging Area (Index) enthält Änderungen für den nächsten Commit; ein Commit ist ein gespeicherter Snapshot mit Nachricht; ein Branch ist eine bewegliche Entwicklungslinie; ein Remote ist eine Referenz auf ein entferntes Repository, normalerweise `origin`. Push sendet lokale Commits, Pull holt und integriert Remoteänderungen, Merge verbindet Historien und Rebase setzt lokale Commits auf eine neue Basis und schreibt ihre IDs um.

~~~powershell
git init
git status
git add .
git commit -m "Add initial PowerShell script"

git branch --show-current
git switch -c feature/logging

git remote add origin https://github.com/ORG/REPO.git
git push -u origin feature/logging
git pull --rebase
~~~

Klonen Sie bei einem bestehenden Projekt das Repository, erstellen Sie einen fokussierten Branch, prüfen Sie `git diff`, stagen Sie nur beabsichtigte Dateien, prüfen Sie `git diff --staged` und führen Sie dann Commit und Push aus. Merge-Konflikte müssen bewusst aufgelöst, getestet und erst danach abgeschlossen werden.

~~~powershell
git log --oneline --decorate --graph --all
git diff
git diff --staged
git restore --staged .\file.ps1
~~~

Prüfen Sie vor dem Veröffentlichen, dass Dateien und Historie keine Kennwörter, Token, privaten Schlüssel, internen Adressen oder personenbezogenen Daten enthalten. Geheimnisse gehören nie in Git: Das Löschen aus einem Branch entfernt sie nicht aus der Historie.

## 6. Visual Studio Code

Nützliche PowerShell-Werkzeuge sind die offizielle Microsoft-Erweiterung **PowerShell**, Explorer und globale Suche, die Befehlspalette (`Ctrl+Shift+P`), das integrierte Terminal, Source Control für Git, der Debugger und PSScriptAnalyzer für statische Prüfungen.

Öffnen Sie den Projektordner, erstellen Sie eine `.ps1`, wählen Sie die richtige PowerShell-Sitzung/-Version, führen Sie Auswahl oder Datei im integrierten Terminal aus, prüfen Sie Problems und testen Sie sowohl normale als auch fehlerhafte Eingaben. Ein Breakpoint hält die Ausführung **vor** der markierten Zeile an; verwenden Sie Step Over, Step Into, Step Out und Continue, um Variablen, Watch und Call Stack zu untersuchen.

~~~powershell
Install-Module PSScriptAnalyzer -Scope CurrentUser
Invoke-ScriptAnalyzer -Path .\Script.ps1

Get-PSRepository
Find-Module PSScriptAnalyzer | Select-Object Name, Version, Repository
~~~

Die Installation eines Moduls verändert das System und lädt Code aus der PowerShell Gallery. Prüfen Sie daher zuerst Repository und Herausgeber. Debuggen Sie kein nicht vertrauenswürdiges Skript als Administrator: Auch der Debugger führt dessen Code aus.

## 7. Steuerung des Ausführungsflusses

### if / elseif / else

~~~powershell
$freeSpaceGB = 12

if ($freeSpaceGB -lt 5) {
    'Critical'
}
elseif ($freeSpaceGB -lt 20) {
    'Warning'
}
else {
    'OK'
}
~~~

PowerShell prüft Bedingungen von oben nach unten. Der erste passende Block wird ausgeführt; die übrigen werden übersprungen.

Mehrere Bedingungen:

~~~powershell
$enabled = $true
$role = 'Analyst'

if ($enabled -and ($role -eq 'Analyst')) {
    'Access condition passed'
}
~~~

Klammern zeigen die Auswertungsreihenfolge. Das ist besonders wichtig, wenn `-and` und `-or` gemeinsam verwendet werden.

### foreach

~~~powershell
$websites = 'google.com', 'microsoft.com', 'example.org'

foreach ($site in $websites) {
    $online = Test-Connection -ComputerName $site -Count 1 -Quiet
    "{0}: {1}" -f $site, $(if ($online) { 'online' } else { 'unreachable' })
}
~~~

Im Unterricht wird das Wort *ping* verwendet. Unter Windows ist das normalerweise das externe Programm `ping.exe`, kein Cmdlet. Für Skripte ist `Test-Connection` besser geeignet, weil es Objekte zurückgibt und PowerShell-Parameter unterstützt.

### Klassisches for

~~~powershell
for ($number = 0; $number -le 25; $number++) {
    "Number is $number"
}
~~~

### while, do...while, do...until

~~~powershell
$attempt = 0
while ($attempt -lt 3) {
    $attempt++
    "Attempt $attempt"
}

do {
    $value = Read-Host 'Enter q to quit'
} while ($value -ne 'q')

do {
    $value = Read-Host 'Enter READY'
} until ($value -eq 'READY')
~~~

Anders als `while` führen `do...`-Schleifen ihren Rumpf mindestens einmal aus.

Das Zahlenratespiel aus dem Unterricht in vollständiger Form:

~~~powershell
$number = Get-Random -Minimum 1 -Maximum 6

do {
    [int]$guess = Read-Host 'Guess a number from 1 to 5'

    if ($guess -lt $number) {
        'Too low'
    }
    elseif ($guess -gt $number) {
        'Too high'
    }
} until ($guess -eq $number)

'Correct'
~~~

- `Get-Random -Minimum 1 -Maximum 6` gibt eine Ganzzahl von 1 bis 5 zurück; die obere Grenze ist ausgeschlossen.
- `Read-Host` gibt einen String zurück; `[int]` wandelt die Eingabe daher in eine Zahl um.
- `-lt` bedeutet „kleiner als“, `-gt` „größer als“, `-eq` „gleich“.
- `do` garantiert mindestens einen Versuch.
- `until` wiederholt den Block, bis die Bedingung **wahr** wird.

Bei Produktionseingaben kann die Konvertierung `[int]` einen Fehler auslösen. `TryParse` ist sicherer:

~~~powershell
$parsed = 0
$valid = [int]::TryParse((Read-Host 'Enter a number'), [ref]$parsed)

if (-not $valid) {
    Write-Warning 'Not a valid integer'
}
~~~

### break, continue, return

~~~powershell
foreach ($item in 1..10) {
    if ($item -eq 3) { continue } # aktuelle Iteration überspringen
    if ($item -gt 7) { break }    # Schleife verlassen
    $item
}

function Get-FirstEvenNumber {
    param([int[]]$Numbers)

    foreach ($number in $Numbers) {
        if ($number % 2 -eq 0) {
            return $number        # Funktion verlassen und Wert zurückgeben
        }
    }
}
~~~

`continue` ist nicht das „Gegenteil“ von `break`: Es geht zur nächsten Iteration, während `break` die Schleife beendet. `return` beendet normalerweise eine Funktion oder einen Scriptblock, nicht nur eine Schleife.

### Vergleichsoperatoren

Vergleichsoperatoren liefern für einen einzelnen Wert `$true`/`$false` und können eine Sammlung filtern, wenn die Sammlung links steht.

#### Gleichheit und Reihenfolge

| Operator | Englische Bezeichnung | Bedeutung | Beispiel | Ergebnis |
|---|---|---|---|---|
| -eq | equal | gleich | 5 -eq 5 | $true |
| -ne | not equal | ungleich | 5 -ne 3 | $true |
| -gt | greater than | größer als | 10 -gt 3 | $true |
| -ge | greater or equal | größer oder gleich | 10 -ge 10 | $true |
| -lt | less than | kleiner als | 2 -lt 5 | $true |
| -le | less or equal | kleiner oder gleich | 5 -le 5 | $true |

Beispiele in Bedingungen:

~~~powershell
$age = 20

if ($age -ge 18) {
    'Adult'
}

$cpu = 75
if ($cpu -gt 90) {
    'Critical'
}
elseif ($cpu -gt 70) {
    'High'
}
else {
    'Normal'
}
~~~

PowerShell verwendet `-eq` statt `=`, weil `=` einen Wert zuweist (`$x = 5`), während `-eq` vergleicht (`$x -eq 5`). Strings werden standardmäßig ohne Beachtung der Groß-/Kleinschreibung verglichen:

~~~powershell
'Admin' -eq 'admin'     # $true
'Admin' -ceq 'admin'    # $false: c = case-sensitive
'Admin' -ieq 'admin'    # $true: i = explizit case-insensitive
~~~

Die Präfixe `c` und `i` funktionieren auch mit anderen String-Operatoren: `-cne`, `-clike`, `-cmatch`, `-ilike` usw. Achten Sie auf die Typen:

~~~powershell
10 -gt 2              # numerischer Vergleich: $true
'10' -gt '2'          # Stringvergleich: Ergebnis folgt der Stringreihenfolge
[int]'10' -gt 2       # explizit numerischer Vergleich
~~~

#### Wildcards: -like und -notlike

`-like` vergleicht mit einem Wildcard-Muster:

| Symbol | Bedeutung |
|---|---|
| * | beliebig viele beliebige Zeichen |
| ? | genau ein beliebiges Zeichen |
| [abc] | ein Zeichen aus der Menge |
| [a-z] | ein Zeichen aus dem Bereich |

~~~powershell
'server01' -like 'server*'      # $true
'server01' -like 'server??'     # $true
'server01' -notlike 'client*'   # $true

Get-Service -Name 'Win*'
Get-ChildItem -Filter '*.ps1'
~~~

#### Reguläre Ausdrücke: -match, -notmatch und -replace

`-match` verwendet einen regulären Ausdruck, keine Wildcard:

~~~powershell
'server-042' -match '^server-\d{3}$'    # $true
'admin@example.com' -match '@'          # $true
'server01' -notmatch '^client'          # $true
~~~

Nach einem erfolgreichen `-match` für einen einzelnen String stehen Gruppen in `$Matches` zur Verfügung:

~~~powershell
if ('server-042' -match '^([a-z]+)-(\d+)$') {
    $Matches[0]   # server-042 — vollständige Übereinstimmung
    $Matches[1]   # server
    $Matches[2]   # 042
}
~~~

Ersetzen per Regex:

~~~powershell
'user@example.com' -replace '@.*$', '@redacted'
# user@redacted
~~~

#### Sammlungen: -contains, -in, -notcontains, -notin

Die Richtung ist wichtig:

~~~powershell
$roles = 'User', 'Analyst', 'Admin'

$roles -contains 'Admin'       # Sammlung enthält den Wert
'Admin' -in $roles             # Wert befindet sich in der Sammlung
$roles -notcontains 'Guest'
'Guest' -notin $roles
~~~

`-contains` erwartet die Sammlung links. `-in` ist in `if` oft besser lesbar:

~~~powershell
if ($currentRole -in 'Analyst', 'Admin') {
    'Allowed'
}
~~~

#### Vergleich einer Sammlung mit einem gewöhnlichen Operator

Wenn eine Sammlung links steht, geben `-eq` und andere gewöhnliche Operatoren die passenden Elemente statt eines Boolean zurück:

~~~powershell
$numbers = 1, 2, 3, 4, 5
$numbers -gt 3       # gibt 4 und 5 zurück
$numbers -eq 3       # gibt 3 zurück
~~~

Um mit einem Boolean-Ergebnis auf ein vorhandenes Element zu prüfen, verwenden Sie `-contains`/`-in`.

#### Typprüfung: -is und -isnot

~~~powershell
42 -is [int]                # $true
'42' -is [string]           # $true
(Get-Date) -is [datetime]   # $true
'42' -isnot [int]           # $true
~~~

#### Logische Operatoren

| Operator | Wann $true |
|---|---|
| -and | beide Bedingungen sind wahr |
| -or | mindestens eine Bedingung ist wahr |
| -xor | genau eine von zwei Bedingungen ist wahr |
| -not oder ! | negiert eine Bedingung |

~~~powershell
($age -ge 18) -and ($enabled -eq $true)
($role -eq 'Admin') -or ($role -eq 'Analyst')
($a -eq $true) -xor ($b -eq $true)
-not (Test-Path .\missing.txt)
!(Test-Path .\missing.txt)
~~~

`-and` und `-or` verwenden Kurzschlussauswertung: Ist links von `-and` `$false`, wird die rechte Seite nicht ausgewertet; ist links von `-or` `$true`, wird die rechte Seite nicht ausgewertet. Damit lässt sich zuerst sicher prüfen, ob ein Objekt vorhanden ist:

~~~powershell
if (($null -ne $service) -and ($service.Status -eq 'Running')) {
    'Running'
}
~~~

#### Arithmetik und Zuweisung

| Operator | Bedeutung |
|---|---|
| + | Addition oder Verkettung |
| - | Subtraktion |
| * | Multiplikation |
| / | Division |
| % | Rest der Division |
| ++ / -- | um 1 erhöhen/verringern |
| += / -= / *= / /= / %= | Operation ausführen und Ergebnis zuweisen |

~~~powershell
$number = 5
$number++       # 6
$number += 4    # 10

10 % 2          # 0 — gerade Zahl
11 % 2          # 1 — ungerade Zahl

$text = 'Power'
$text += 'Shell' # PowerShell
~~~

Der Ausdruck `$number % 2 -eq 0` im `return`-Beispiel bedeutet: „Der Rest bei der Division durch 2 ist null“, die Zahl ist also gerade.

#### Operatorrangfolge

Verlassen Sie sich bei einem komplexen Ausdruck nicht auf Ihr Gedächtnis; verwenden Sie Klammern:

~~~powershell
if (($cpu -gt 80) -and (($status -eq 'Running') -or $force)) {
    ...
}
~~~

Für die vollständige integrierte Hilfe:

~~~powershell
Get-Help about_Comparison_Operators
Get-Help about_Logical_Operators
Get-Help about_Arithmetic_Operators
Get-Help about_Operator_Precedence
~~~

## 8. Fehlerbehandlung

`try`/`catch`/`finally` behandelt terminierende Fehler. Viele Cmdlets erzeugen standardmäßig einen nicht terminierenden Fehler; fügen Sie deshalb `-ErrorAction Stop` hinzu, wenn ein zuverlässiges `catch` erforderlich ist.

~~~powershell
try {
    $service = Get-Service -Name 'DefinitelyMissing' -ErrorAction Stop
    $service
}
catch [Microsoft.PowerShell.Commands.ServiceCommandException] {
    Write-Warning "Service not found: $($_.Exception.Message)"
}
catch { Write-Error "Unexpected error: $($_.Exception.Message)" }
finally { Write-Verbose 'Cleanup complete' }
~~~

Nützliche Objekte und Einstellungen sind `$Error[0]` (letzter Fehlerdatensatz), `$_.Exception.Message` (Meldung in `catch`), `$PSItem.InvocationInfo` (Fundort) und `$ErrorActionPreference` (Sitzungseinstellung). Setzen Sie `$ErrorActionPreference = 'SilentlyContinue'` nicht für ein ganzes Skript: Das verbirgt Probleme. Behandeln Sie erwartete Fehler lokal.

### PowerShell-Ausgabeströme

| Stream | Befehl | Zweck |
|---|---|---|
| Success (1) | `Write-Output` oder gewöhnlicher Ausdruck | Daten für Funktion/Pipeline |
| Error (2) | `Write-Error` | Fehler |
| Warning (3) | `Write-Warning` | Warnungen |
| Verbose (4) | `Write-Verbose` | detaillierte Diagnose mit `-Verbose` |
| Debug (5) | `Write-Debug` | Debug-Meldungen |
| Information (6) | `Write-Information` | Informationsmeldungen |
| Host | `Write-Host` | Anzeige für Menschen |

~~~powershell
.\Script.ps1 > .\output.txt       # Erfolgsausgabe
.\Script.ps1 2> .\errors.txt      # Fehlerstream
.\Script.ps1 *> .\all-streams.txt # alle umleitbaren Streams
~~~

Ein **terminierender Fehler** hält die aktuelle Operation an und kann abgefangen werden. Ein **nicht terminierender Fehler** wird in den Error-Stream geschrieben, während das Skript weiterlaufen kann. Wichtige `ErrorAction`-Werte sind `Continue`, `Stop`, `SilentlyContinue`, `Ignore` und `Inquire`. Bewahren Sie den Kontext in `catch` und werfen Sie erneut, wenn der Aufrufer den Fehlschlag kennen muss.

~~~powershell
$session = $null
try {
    $session = New-PSSession -ComputerName 'server01' -ErrorAction Stop
    Invoke-Command -Session $session -ScriptBlock { Get-Service }
} finally {
    if ($null -ne $session) { Remove-PSSession -Session $session }
}
~~~

## 9. Schleifendemonstrationen aus dem Kurs

~~~powershell
for ($number = 0; $number -le 25; $number++) { Write-Output "Number is $number" }
for ($characters = ''; $characters.Length -le 15; $characters += '5') {
    Write-Host $characters
    Start-Sleep -Milliseconds 100
}
~~~

Ein Muster für echte Massenoperationen sollte `ShouldProcess`, Protokollierung und Fehlerbehandlung enthalten. Starten Sie zuerst mit `-WhatIf`, wenn der Befehl es unterstützt.

~~~powershell
[CmdletBinding(SupportsShouldProcess)]
param([Parameter(Mandatory)][string]$ComputerListPath)
$computers = Import-Csv -LiteralPath $ComputerListPath
foreach ($computer in $computers) {
    try {
        if ($PSCmdlet.ShouldProcess($computer.Name, 'Run remote audit')) {
            Invoke-Command -ComputerName $computer.Name -ScriptBlock { Get-Service | Where-Object Status -EQ 'Running' } -ErrorAction Stop
        }
    } catch { Write-Warning "[$($computer.Name)] $($_.Exception.Message)" }
}
~~~

## 10. PowerShell-Sicherheit

### Prinzip der geringsten Privilegien

- Normale Benutzer benötigen weder Global Admin noch Domain Admin.
- Administrations- und Alltagskonten müssen getrennt sein.
- Rechte werden über sauber entworfene Gruppen vergeben; Skripte und Automatisierung erhalten nur notwendige Berechtigungen.
- Privilegienänderungen müssen protokolliert und geprüft werden.

### Windows Features

Das ServerManager-Modul stellt unter Windows Server Folgendes bereit:

~~~powershell
Get-WindowsFeature
Install-WindowsFeature -Name Web-Server -WhatIf
Uninstall-WindowsFeature -Name Web-Server -WhatIf
~~~

Diese Cmdlets verwalten **Windows-Server**-Rollen und -Features, nicht allgemeine Benutzerrollen.

### Skriptsignierung und Härtung

~~~powershell
$certificate = Get-ChildItem Cert:\CurrentUser\My -CodeSigningCert | Select-Object -First 1
Set-AuthenticodeSignature -FilePath .\Script.ps1 -Certificate $certificate
Get-AuthenticodeSignature .\Script.ps1
~~~

Eine Organisation benötigt ein korrekt ausgestelltes, vertrauenswürdiges Zertifikat, einen geschützten privaten Schlüssel sowie Laufzeit- und Widerrufsverwaltung. Eine Signatur bestätigt Urheberschaft und Integrität nach dem Signieren, nicht die Sicherheit des Codes.

Prüfen Sie den Sprachmodus mit `$ExecutionContext.SessionState.LanguageMode`. Constrained Language Mode wirkt als Teil von WDAC/AppLocker, nicht als manuell gesetzte Variable in einer potenziell feindlichen Sitzung. Zusätzliche Härtung: WDAC/AppLocker, Script-Block-/Module-Logging und Transcription, AMSI, aktueller Endpunktschutz, JEA, geschütztes Remoting, Deaktivierung von PowerShell v2 sowie zentrale Ereignissammlung und Warnungen.

## 12. Red Team: die Rolle von PowerShell

Der Kurs gibt nur einen Überblick. PowerShell wird nach dem Erstzugang häufig für Aufklärung, Codeausführung, Privilegienausweitung, seitliche Bewegung und Datensammlung genutzt. PowerShell Empire und PowerSploit werden als historisch bekannte Post-Exploitation-/Penetration-Testing-Werkzeugsätze genannt. Genau diese Möglichkeiten machen Logging und Einschränkung von PowerShell für Blue Teams wichtig.

Für die Verteidigung: ungewöhnliche Argumente, Encoded Commands und Policy-Bypässe überwachen; Script Block Logging und die Kette „Elternprozess → PowerShell → Netzwerk/Kindprozess“ analysieren; Privilegien, ausgehende Verbindungen und Remoteverwaltung beschränken; Allowlisting, JEA, EDR und zentrales SIEM nutzen. Offensive Tests nur im Labor oder in einem ausdrücklich freigegebenen Scope durchführen.

## 13. REST-APIs aus PowerShell

Die wichtigsten HTTP-Methoden sind `GET` (Ressource lesen), `POST` (erstellen oder Operation starten), `PUT` (ersetzen), `PATCH` (teilweise ändern) und `DELETE` (löschen). Die genaue Semantik bestimmt die API-Dokumentation.

~~~powershell
$uri = 'https://api.github.com/repos/PowerShell/PowerShell'
$headers = @{ Accept = 'application/vnd.github+json' }
$repository = Invoke-RestMethod -Method Get -Uri $uri -Headers $headers
$repository | Select-Object full_name, stargazers_count, open_issues_count
~~~

`$uri` enthält einen Endpunkt, `$headers` ist eine Hashtable mit HTTP-Headern, und `Invoke-RestMethod` wandelt JSON in ein PowerShell-Objekt um. Verwenden Sie HTTPS und übertragen Sie Token niemals über HTTP. Eine gewöhnliche HTTP/HTTPS-Anfrage benötigt keine Administratorrechte.

`@{ ... }` erzeugt eine **Hashtable**, kein JSON; `ConvertTo-Json` konvertiert sie. `@parameters` ist Splatting: Hashtable-Schlüssel werden zu benannten Befehlsparametern.

~~~powershell
$body = @{ meal = 'pizza'; cook = 'Barbara' }
$parameters = @{ Method='Post'; Uri='https://api.example.test/meals'; ContentType='application/json'; Body=$body | ConvertTo-Json -Depth 5; ErrorAction='Stop' }
try { Invoke-RestMethod @parameters } catch { Write-Error "API request failed: $($_.Exception.Message)" }
~~~

Header bleiben Hashtables; wandeln Sie sie nicht in JSON um. Token und Kennwörter gehören nie in `.ps1`, Git oder den Terminalverlauf. Nutzen Sie SecretManagement, CI/CD-Secrets oder einen freigegebenen Vault. Behandeln Sie HTTP 2xx/4xx/5xx gemäß API-Dokumentation, folgen Sie Pagination-Links/-Token, deaktivieren Sie keine TLS-Zertifikatsprüfung und wiederholen Sie nicht-idempotente `POST`/`DELETE`-Operationen nicht blind.

`Invoke-RestMethod` eignet sich für JSON/XML-APIs und liefert normalerweise Objekte; `Invoke-WebRequest` liefert eine allgemeinere HTTP-Antwort, wenn Header, Status, HTML oder eine Datei wichtig sind.

## 17. Abschließende praktische Vorlage

Dieser Rahmen verbindet Parameter, Eingabevalidierung, Verbose-Ausgabe, Fehlerbehandlung, Objekte und einen sicheren Dry Run:

~~~powershell
[CmdletBinding(SupportsShouldProcess)]
param([Parameter(Mandatory)][ValidateScript({ Test-Path -LiteralPath $_ -PathType Leaf })][string]$ComputerListPath, [ValidateRange(1, 10)][int]$Count = 1)
Set-StrictMode -Version Latest
$ErrorActionPreference = 'Stop'
try {
    $computers = Get-Content -LiteralPath $ComputerListPath | Where-Object { -not [string]::IsNullOrWhiteSpace($_) } | Sort-Object -Unique
    foreach ($computer in $computers) {
        if ($PSCmdlet.ShouldProcess($computer, 'Test connectivity')) {
            $online = Test-Connection -ComputerName $computer -Count $Count -Quiet -ErrorAction Stop
            [pscustomobject]@{ ComputerName=$computer; Online=$online; CheckedAt=Get-Date }
        }
    }
} catch { Write-Error "Audit failed: $($_.Exception.Message)"; throw }
~~~

Beispiel für eine sichere Prüfung: `.\Audit-Hosts.ps1 -ComputerListPath .\hosts.txt -Verbose -WhatIf`.

## 18. Was im Kurs korrigiert werden sollte

- `$name` ist eine Variable, keine „Pipe-Variable“; eine Pipeline entsteht nur durch ein explizites `|`.
- Windows-`ping` ist normalerweise `ping.exe`; das Objekt-Cmdlet ist `Test-Connection`.
- Aliases sind interaktiv praktisch, in Lern- und Produktionsskripten sind volle Namen besser.
- `RemoteSigned` benötigt normalerweise nur `CurrentUser`; Execution Policy ist keine Sicherheitsgrenze und von UAC verschieden.
- Führen Sie PowerShell nicht standardmäßig als Administrator aus; erhöhen Sie Rechte nur für die konkrete Operation.
- Ohne `-ErrorAction Stop` fängt `catch` nicht alle nicht terminierenden Fehler; `continue` überspringt eine Iteration.
- `PUT` ersetzt normalerweise, `PATCH` ändert teilweise. Eine Hashtable ist kein JSON; Header bleiben Hashtables und dürfen kein Klartext-Kennwort enthalten.
- Die im Unterricht gezeigte .NET-Interactive/Polyglot-Notebooks-Erweiterung für VS Code wurde 2026 eingestellt.
- PowerShell Empire/PowerSploit nur im autorisierten Labor; für moderne Verteidigung sind Telemetrie, Allowlisting, JEA und minimale Privilegien wichtiger.
