## 1. Quick start

### What PowerShell is

PowerShell combines a command shell and a scripting language. Commands usually return .NET objects rather than plain text. This allows objects to be passed through the pipeline and their properties to be accessed without manually parsing strings.

Full cmdlet names follow the Verb-Noun pattern:

~~~powershell
Get-Process
Get-Service
Set-ExecutionPolicy
Invoke-RestMethod
~~~

The correct term is **cmdlet**. Windows PowerShell 5.1 is built into current versions of Windows; PowerShell 7 is a separate cross-platform product that can be installed separately when needed.

### How to read a PowerShell command

Break this line into parts:

~~~powershell
Get-Process -Name 'powershell' -ErrorAction SilentlyContinue
~~~

- `Get-Process` is the cmdlet name: the `Get` verb means retrieve, and `Process` is the noun.
- `-Name` is a named parameter.
- `'powershell'` is the value of the Name parameter.
- `-ErrorAction` is a common parameter that controls behaviour for a non-terminating error.
- `SilentlyContinue` is the ErrorAction value: do not display the error and continue. Do not use it in real scripts without a reason.

Discover syntax and parameter sets:

~~~powershell
Get-Command Get-Process -Syntax
Get-Help Get-Process -Parameter Name
Get-Help about_CommonParameters
~~~

Prefer named parameters. A positional form is shorter but less obvious:

~~~powershell
Get-Process -Name 'powershell'  # clear
Get-Process 'powershell'        # works positionally, but is less explicit
~~~

A switch parameter is a flag without a separate value:

~~~powershell
Get-ChildItem -Recurse -Force
~~~

Here `-Recurse` traverses subfolders, while `-Force` shows hidden items.

### Core syntax symbols

| Syntax | Meaning |
|---|---|
| `$name` | variable |
| `-Name` | command parameter |
| `'text'` | string without variable expansion |
| `"text $name"` | string with variable expansion |
| `$(...)` | evaluate an expression within a string or another expression |
| `(...)` | group an expression or obtain a command result first |
| `{...}` | code block: body of a function, loop, condition, or ScriptBlock |
| `@()` | always create an array |
| `@{ Key = Value }` | create a hashtable: a key/value collection |
| `[type]` | specify or check a type |
| `.Property` | access an object property |
| `.Method()` | call a method |
| `\|` | pass objects to the next command |
| `&` | call operator: run a command/script whose path is an expression |
| `#` | single-line comment |
| `<# ... #>` | multi-line comment or comment-based help |

Example combining several constructs:

~~~powershell
$serviceName = 'WinRM'
$service = Get-Service -Name $serviceName

if ($service.Status -eq 'Running') {
    "Service $($service.Name) is running"
}
~~~

The dot in `$service.Status` accesses the Status property. `$($service.Name)` evaluates an expression more complex than a simple variable inside a double-quoted string.

### Variables and data types

Create a variable by assignment:

~~~powershell
$name = 'server01'
$count = 3
$enabled = $true
$checkedAt = Get-Date
~~~

Inspect types:

~~~powershell
$name.GetType().FullName
$count.GetType().FullName
$checkedAt.GetType().FullName
~~~

Types can be specified explicitly:

~~~powershell
[string]$computerName = 'server01'
[int]$retryCount = 3
[bool]$enabled = $true
[datetime]$deadline = '2026-08-20'
~~~

Common types are `[string]` (text), `[int]` (integer), `[double]` (decimal number), `[bool]` (Boolean), `[datetime]` (date and time), `[array]`/`[object[]]` (ordered collection), `[hashtable]` (key/value pairs), and `[pscustomobject]` (an object with named properties).

PowerShell often converts types automatically, but avoid relying on ambiguous conversions:

~~~powershell
'10' + '2'        # '102': string concatenation
[int]'10' + 2     # 12: numeric addition
~~~

### Strings, arrays, hashtables, and PSCustomObject

Single quotes preserve literal text. Double quotes expand variables and subexpressions:

~~~powershell
$name = 'server01'

'Computer: $name'             # Computer: $name
"Computer: $name"             # Computer: server01
"Length: $($name.Length)"     # Length: 8
~~~

An array, including the range operator and a guaranteed array expression:

~~~powershell
$computers = 'server01', 'server02', 'server03'
$computers[0]
$computers[-1]
$computers.Count
$computers += 'server04'

foreach ($computer in $computers) {
    $computer
}

1..5
5..1

$services = @(Get-Service -Name 'WinRM')
$services.Count
~~~

A hashtable is useful for settings and command parameters. Passing it to a command with `@settings` is **splatting**: its keys become parameter names and its values become arguments.

~~~powershell
$settings = @{
    ComputerName = 'server01'
    Count        = 1
    Quiet        = $true
}

$settings['ComputerName']
$settings.ComputerName
Test-Connection @settings

$result = [pscustomobject]@{
    ComputerName = 'server01'
    Online       = $true
    CheckedAt    = Get-Date
}

$result.Online
$result | Format-List
$result | Export-Csv .\result.csv -NoTypeInformation
~~~

`$null` means that a value is absent. Put `$null` on the left of a comparison so that comparing against a collection remains unambiguous:

~~~powershell
$value = $null

if ($null -eq $value) {
    'Value is absent'
}
~~~

### Find commands, navigate, and use the object pipeline

Aliases are convenient interactively, but use full cmdlet names in persisted scripts: `Get-ChildItem`, not `ls`; `Get-Location`, not `pwd`. This makes code easier to read and transfer.

~~~powershell
Get-Command -Noun Process
Get-Command -Name '*Service*'
Get-Help Get-Process -Examples
Get-Alias
Get-Alias pwd
Get-Alias ls

Get-Location
Get-ChildItem
Set-Location C:\Users
Set-Location ..
Clear-Host
~~~

The pipeline passes the result of one command to the next as objects:

~~~powershell
Get-Process |
    Where-Object CPU -GT 10 |
    Sort-Object CPU -Descending |
    Select-Object -First 10 Name, Id, CPU
~~~

Inspect an object's type and properties before processing it:

~~~powershell
Get-Process | Get-Member
Get-Service | Select-Object -First 5 | Format-Table Name, Status, StartType
~~~

`Format-Table` and `Format-List` are for final display; do not place them in the middle of a pipeline that must continue processing objects.

`foreach ($item in $items)` is a language construct and usually uses a collection already in memory. `ForEach-Object { ... }` is a pipeline cmdlet that processes incoming objects as they arrive. Pipeline binding can occur **ByValue** when an object's type matches a parameter, or **ByPropertyName** when an object's property name matches a parameter name.

~~~powershell
Get-Help Stop-Service -Full

[pscustomobject]@{ Name = 'Spooler' } |
    Stop-Service -WhatIf
~~~

Here the `Name` property binds to the `-Name` parameter. Correct property names therefore matter in PowerShell objects.

## 2. How to read existing scripts

PowerShell scripts use the `.ps1` extension. When reviewing another person's code, work from top to bottom:

1. Read help comments: `.SYNOPSIS`, `.DESCRIPTION`, `.PARAMETER`, and `.EXAMPLE`.
2. Find `param(...)` and understand inputs and mandatory parameters.
3. List variables; they start with `$`.
4. Find functions, loops, conditions, and remote-execution points.
5. Use `Get-Help` and `Get-Command` for unfamiliar commands.
6. Check external addresses, files, modules, permissions, and possible side effects.
7. Run static analysis and test without administrator rights in an isolated environment.

Minimal documented script:

~~~powershell
<#
.SYNOPSIS
Tests availability of hosts from a text file.

.PARAMETER Path
Path to a file containing one name or IP address per line.

.EXAMPLE
.\Test-Hosts.ps1 -Path .\hosts.txt
#>

[CmdletBinding()]
param(
    [Parameter(Mandatory)]
    [ValidateScript({ Test-Path -LiteralPath $_ -PathType Leaf })]
    [string]$Path
)

$computers = Get-Content -LiteralPath $Path

foreach ($computer in $computers) {
    $online = Test-Connection -ComputerName $computer -Count 1 -Quiet

    [pscustomobject]@{
        ComputerName = $computer
        Online       = $online
        CheckedAt    = Get-Date
    }
}
~~~

Use `Write-Verbose` for diagnostic messages in an advanced script/function; users enable them with `-Verbose`. Return objects for data instead of printing strings through `Write-Host`.

## 3. Functions

Functions make code reusable. A minimal example:

~~~powershell
function Show-PowerShellInfo {
    $PSVersionTable.PSVersion
    Get-Location
}

Show-PowerShellInfo
~~~

Practical advanced function:

~~~powershell
function Test-HostOnline {
    [CmdletBinding()]
    param(
        [Parameter(Mandatory, ValueFromPipeline)]
        [ValidateNotNullOrEmpty()]
        [string[]]$ComputerName
    )

    process {
        foreach ($computer in $ComputerName) {
            [pscustomobject]@{
                ComputerName = $computer
                Online       = Test-Connection -ComputerName $computer -Count 1 -Quiet
            }
        }
    }
}

'server01', 'server02' | Test-HostOnline
~~~

`[CmdletBinding()]` adds common parameters such as `-Verbose`, `-Debug`, and `-ErrorAction`; `param(...)` is the function contract; `[string[]]` accepts one or many strings; `ValueFromPipeline` permits input via `|`; `process` handles incoming pipeline items; and `[pscustomobject]` returns structured results.

Validate input with attributes such as `[ValidateNotNullOrEmpty()]`, `[ValidateRange(1, 10)]`, and `[ValidateSet('Info', 'Warning', 'Error')]`. A function returns all normal success output, not only a value following `return`. Use `return` to end the current function/script block. Return objects directly or with `Write-Output`; reserve `Write-Host` for UI messages and `Write-Verbose` for diagnostics.

Name functions with `ApprovedVerb-Noun` (`Get-Verb` lists approved verbs), declare and type parameters, return objects rather than formatted text, and do not require administrator rights unless necessary.

### Run a `.ps1`

~~~powershell
# From the current directory
.\Hello-Friends.ps1

# Full path; & is required when the path is stored in a string
& 'C:\Users\User\Downloads\Hello Friends.ps1'

# Pass parameters
& 'C:\Scripts\Test-Hosts.ps1' -Path 'C:\Data\hosts.txt'
~~~

## 4. Execution Policy and safe execution

Check policy by scope:

~~~powershell
Get-ExecutionPolicy -List
~~~

PowerShell policies are `AllSigned`, `RemoteSigned`, `Restricted`, `Unrestricted`, `Bypass`, `Undefined`, and `Default`. Scope precedence is `MachinePolicy`, `UserPolicy`, `Process`, `CurrentUser`, then `LocalMachine`; Group Policy can override local settings.

For a learning computer, it is safer to change only the current user's policy:

~~~powershell
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
~~~

For a trusted downloaded file:

~~~powershell
Get-FileHash .\TrustedScript.ps1 -Algorithm SHA256
Unblock-File .\TrustedScript.ps1
~~~

Execution Policy protects against accidental execution, not against a determined attacker. Do not change `LocalMachine` when `CurrentUser` or `Process` is sufficient; do not use `Bypass` permanently; inspect code, source, and hash before running it without elevation; and use a disposable VM or Windows Sandbox for untrusted code.

## 5. Git and version control

Git stores change history; GitHub is a service for hosting Git repositories and collaborating on them.

~~~text
working directory → staging area → local commit → remote repository
      git add          git commit         git push
~~~

The working directory contains edited files; the staging area (index) contains changes selected for the next commit; a commit is a saved snapshot with a message; a branch is a movable development line; a remote is a link to a remote repository, normally `origin`. Push sends local commits; pull receives and integrates remote changes; merge combines histories; rebase moves local commits onto a new base and rewrites their IDs.

~~~powershell
git init
git status
git add .
git commit -m "Add initial PowerShell script"

git branch --show-current
git switch -c feature/logging

git remote add origin https://github.com/ORG/REPO.git
git push -u origin feature/logging
git pull --rebase
~~~

For an existing project, clone it, create a focused branch, inspect `git diff`, stage only intended files, inspect `git diff --staged`, then commit and push. Resolve merge conflicts deliberately, test, and only then complete the merge or rebase.

~~~powershell
git log --oneline --decorate --graph --all
git diff
git diff --staged
git restore --staged .\file.ps1
~~~

Before publishing, verify that files and history contain no passwords, tokens, private keys, internal addresses, or personal data. Secrets must never be kept in Git: deleting them from a branch does not remove them from history.

## 6. Visual Studio Code

Useful PowerShell tooling includes Microsoft's official **PowerShell** extension, Explorer and global search, the command palette (`Ctrl+Shift+P`), the integrated terminal, Source Control for Git, the debugger, and PSScriptAnalyzer for static checks.

Open the project folder, create a `.ps1` file, choose the correct PowerShell session/version, run selected code or the file in the integrated terminal, inspect Problems, and test both normal and error input. A breakpoint stops execution **before** the marked line; use Step Over, Step Into, Step Out, and Continue to inspect variables, Watch, and Call Stack.

~~~powershell
Install-Module PSScriptAnalyzer -Scope CurrentUser
Invoke-ScriptAnalyzer -Path .\Script.ps1

Get-PSRepository
Find-Module PSScriptAnalyzer | Select-Object Name, Version, Repository
~~~

Installing a module changes the system and downloads code from PowerShell Gallery, so check the repository and publisher first. Never debug an untrusted script as administrator: the debugger still executes its code.

## 7. Controlling the Flow of Execution

### if / elseif / else

~~~powershell
$freeSpaceGB = 12

if ($freeSpaceGB -lt 5) {
    'Critical'
}
elseif ($freeSpaceGB -lt 20) {
    'Warning'
}
else {
    'OK'
}
~~~

PowerShell evaluates conditions from top to bottom. The first matching block runs and the remaining blocks are skipped.

Multiple conditions:

~~~powershell
$enabled = $true
$role = 'Analyst'

if ($enabled -and ($role -eq 'Analyst')) {
    'Access condition passed'
}
~~~

Parentheses make the evaluation order explicit. This is especially important when `-and` and `-or` are used together.

### foreach

~~~powershell
$websites = 'google.com', 'microsoft.com', 'example.org'

foreach ($site in $websites) {
    $online = Test-Connection -ComputerName $site -Count 1 -Quiet
    "{0}: {1}" -f $site, $(if ($online) { 'online' } else { 'unreachable' })
}
~~~

The lesson uses the word *ping*, but in Windows that is normally the external `ping.exe` program rather than a cmdlet. In scripts, prefer `Test-Connection` because it returns objects and supports PowerShell parameters.

### Classic for

~~~powershell
for ($number = 0; $number -le 25; $number++) {
    "Number is $number"
}
~~~

### while, do...while, do...until

~~~powershell
$attempt = 0
while ($attempt -lt 3) {
    $attempt++
    "Attempt $attempt"
}

do {
    $value = Read-Host 'Enter q to quit'
} while ($value -ne 'q')

do {
    $value = Read-Host 'Enter READY'
} until ($value -eq 'READY')
~~~

Unlike `while`, `do...` loops run their body at least once.

The lesson's number-guessing game in a complete form:

~~~powershell
$number = Get-Random -Minimum 1 -Maximum 6

do {
    [int]$guess = Read-Host 'Guess a number from 1 to 5'

    if ($guess -lt $number) {
        'Too low'
    }
    elseif ($guess -gt $number) {
        'Too high'
    }
} until ($guess -eq $number)

'Correct'
~~~

- `Get-Random -Minimum 1 -Maximum 6` returns an integer from 1 through 5; the upper boundary is excluded.
- `Read-Host` returns a string, so `[int]` converts the input to a number.
- `-lt` means “less than”, `-gt` “greater than”, and `-eq` “equal”.
- `do` guarantees at least one attempt.
- `until` repeats until its condition becomes **true**.

For production input, `[int]` conversion can throw an error. `TryParse` is safer:

~~~powershell
$parsed = 0
$valid = [int]::TryParse((Read-Host 'Enter a number'), [ref]$parsed)

if (-not $valid) {
    Write-Warning 'Not a valid integer'
}
~~~

### break, continue, return

~~~powershell
foreach ($item in 1..10) {
    if ($item -eq 3) { continue } # skip the current iteration
    if ($item -gt 7) { break }    # leave the loop
    $item
}

function Get-FirstEvenNumber {
    param([int[]]$Numbers)

    foreach ($number in $Numbers) {
        if ($number % 2 -eq 0) {
            return $number        # leave the function and return a value
        }
    }
}
~~~

`continue` is not the “opposite” of `break`: it moves to the next iteration, while `break` ends the loop. `return` normally exits a function or script block, not just a loop.

### Comparison operators

Comparison operators return `$true`/`$false` for one value and can filter a collection when the collection is on the left.

#### Equality and order

| Operator | English name | Meaning | Example | Result |
|---|---|---|---|---|
| -eq | equal | equal | 5 -eq 5 | $true |
| -ne | not equal | not equal | 5 -ne 3 | $true |
| -gt | greater than | greater than | 10 -gt 3 | $true |
| -ge | greater or equal | greater than or equal | 10 -ge 10 | $true |
| -lt | less than | less than | 2 -lt 5 | $true |
| -le | less or equal | less than or equal | 5 -le 5 | $true |

Examples in conditions:

~~~powershell
$age = 20

if ($age -ge 18) {
    'Adult'
}

$cpu = 75
if ($cpu -gt 90) {
    'Critical'
}
elseif ($cpu -gt 70) {
    'High'
}
else {
    'Normal'
}
~~~

PowerShell uses `-eq`, not `=`, because `=` assigns a value (`$x = 5`), whereas `-eq` compares (`$x -eq 5`). By default, strings are compared case-insensitively:

~~~powershell
'Admin' -eq 'admin'     # $true
'Admin' -ceq 'admin'    # $false: c = case-sensitive
'Admin' -ieq 'admin'    # $true: i = explicitly case-insensitive
~~~

The `c` and `i` prefixes also work with other string operators: `-cne`, `-clike`, `-cmatch`, `-ilike`, and so on. Pay attention to types:

~~~powershell
10 -gt 2              # numeric comparison: $true
'10' -gt '2'          # string comparison: result follows string ordering
[int]'10' -gt 2       # explicitly numeric comparison
~~~

#### Wildcards: -like and -notlike

`-like` compares a wildcard pattern:

| Symbol | Meaning |
|---|---|
| * | any number of any characters |
| ? | exactly one arbitrary character |
| [abc] | one character from the set |
| [a-z] | one character from the range |

~~~powershell
'server01' -like 'server*'      # $true
'server01' -like 'server??'     # $true
'server01' -notlike 'client*'   # $true

Get-Service -Name 'Win*'
Get-ChildItem -Filter '*.ps1'
~~~

#### Regular expressions: -match, -notmatch, and -replace

`-match` uses a regular expression, not a wildcard:

~~~powershell
'server-042' -match '^server-\d{3}$'    # $true
'admin@example.com' -match '@'          # $true
'server01' -notmatch '^client'          # $true
~~~

After a successful `-match` for a single string, groups are available in `$Matches`:

~~~powershell
if ('server-042' -match '^([a-z]+)-(\d+)$') {
    $Matches[0]   # server-042 — the full match
    $Matches[1]   # server
    $Matches[2]   # 042
}
~~~

Regex replacement:

~~~powershell
'user@example.com' -replace '@.*$', '@redacted'
# user@redacted
~~~

#### Collections: -contains, -in, -notcontains, -notin

Direction matters:

~~~powershell
$roles = 'User', 'Analyst', 'Admin'

$roles -contains 'Admin'       # the collection contains the value
'Admin' -in $roles             # the value is in the collection
$roles -notcontains 'Guest'
'Guest' -notin $roles
~~~

`-contains` expects the collection on the left. `-in` is often easier to read in `if`:

~~~powershell
if ($currentRole -in 'Analyst', 'Admin') {
    'Allowed'
}
~~~

#### Comparing a collection with an ordinary operator

When a collection is on the left, `-eq` and other ordinary operators return matching elements rather than a Boolean:

~~~powershell
$numbers = 1, 2, 3, 4, 5
$numbers -gt 3       # returns 4 and 5
$numbers -eq 3       # returns 3
~~~

To test whether an element exists with a Boolean result, use `-contains`/`-in`.

#### Type test: -is and -isnot

~~~powershell
42 -is [int]                # $true
'42' -is [string]           # $true
(Get-Date) -is [datetime]   # $true
'42' -isnot [int]           # $true
~~~

#### Logical operators

| Operator | When it is $true |
|---|---|
| -and | both conditions are true |
| -or | at least one condition is true |
| -xor | exactly one of two conditions is true |
| -not or ! | negates a condition |

~~~powershell
($age -ge 18) -and ($enabled -eq $true)
($role -eq 'Admin') -or ($role -eq 'Analyst')
($a -eq $true) -xor ($b -eq $true)
-not (Test-Path .\missing.txt)
!(Test-Path .\missing.txt)
~~~

`-and` and `-or` use short-circuit evaluation: when the left side of `-and` is `$false`, the right side is not evaluated; when the left side of `-or` is `$true`, the right side is not evaluated. This lets you check that an object exists first:

~~~powershell
if (($null -ne $service) -and ($service.Status -eq 'Running')) {
    'Running'
}
~~~

#### Arithmetic and assignment

| Operator | Meaning |
|---|---|
| + | addition or concatenation |
| - | subtraction |
| * | multiplication |
| / | division |
| % | remainder |
| ++ / -- | increment/decrement by 1 |
| += / -= / *= / /= / %= | perform the operation and assign the result |

~~~powershell
$number = 5
$number++       # 6
$number += 4    # 10

10 % 2          # 0 — even number
11 % 2          # 1 — odd number

$text = 'Power'
$text += 'Shell' # PowerShell
~~~

Thus `$number % 2 -eq 0` in the `return` example means “the remainder after division by 2 is zero”, i.e. the number is even.

#### Operator precedence

Do not rely on memory for a complex expression—use parentheses:

~~~powershell
if (($cpu -gt 80) -and (($status -eq 'Running') -or $force)) {
    ...
}
~~~

For the complete built-in reference:

~~~powershell
Get-Help about_Comparison_Operators
Get-Help about_Logical_Operators
Get-Help about_Arithmetic_Operators
Get-Help about_Operator_Precedence
~~~

## 8. Error handling

`try`/`catch`/`finally` handles terminating errors. Many cmdlets produce a non-terminating error by default, so add `-ErrorAction Stop` when a reliable `catch` is required.

~~~powershell
try {
    $service = Get-Service -Name 'DefinitelyMissing' -ErrorAction Stop
    $service
}
catch [Microsoft.PowerShell.Commands.ServiceCommandException] {
    Write-Warning "Service not found: $($_.Exception.Message)"
}
catch {
    Write-Error "Unexpected error: $($_.Exception.Message)"
}
finally {
    Write-Verbose 'Cleanup complete'
}
~~~

Useful objects and settings are `$Error[0]` (the latest error record), `$_.Exception.Message` (the message in `catch`), `$PSItem.InvocationInfo` (the place where it occurred), and `$ErrorActionPreference` (the session-wide setting). Do not set `$ErrorActionPreference = 'SilentlyContinue'` for an entire script: it hides problems. Handle expected errors locally.

### PowerShell output streams

| Stream | Command | Purpose |
|---|---|---|
| Success (1) | `Write-Output` or an ordinary expression | function/pipeline data |
| Error (2) | `Write-Error` | errors |
| Warning (3) | `Write-Warning` | warnings |
| Verbose (4) | `Write-Verbose` | detailed diagnostics enabled by `-Verbose` |
| Debug (5) | `Write-Debug` | debug messages |
| Information (6) | `Write-Information` | information messages |
| Host | `Write-Host` | human-facing display; uses the Information stream since PowerShell 5 |

~~~powershell
.\Script.ps1 > .\output.txt       # success output
.\Script.ps1 2> .\errors.txt      # error stream
.\Script.ps1 *> .\all-streams.txt # all redirectable streams
~~~

A **terminating error** stops the current operation and can be caught. A **non-terminating error** is written to the Error stream while the command or script may continue. Key `ErrorAction` values are `Continue`, `Stop`, `SilentlyContinue`, `Ignore`, and `Inquire`. Preserve context in a `catch` and rethrow when the caller must know that the operation failed:

~~~powershell
catch {
    Write-Error ("Operation failed. Type={0}; Message={1}; Position={2}" -f $_.Exception.GetType().FullName, $_.Exception.Message, $_.InvocationInfo.PositionMessage)
    throw
}
~~~

Use `finally` to free resources whether the operation succeeds or fails:

~~~powershell
$session = $null
try {
    $session = New-PSSession -ComputerName 'server01' -ErrorAction Stop
    Invoke-Command -Session $session -ScriptBlock { Get-Service }
}
finally {
    if ($null -ne $session) { Remove-PSSession -Session $session }
}
~~~

## 9. Loop demonstrations from the course

~~~powershell
for ($number = 0; $number -le 25; $number++) {
    Write-Output "Number is $number"
}

for ($characters = ''; $characters.Length -le 15; $characters += '5') {
    Write-Host $characters
~~~

A real bulk-operation pattern should use `ShouldProcess`, logging, and error handling. Run it with `-WhatIf` first whenever the command supports it.

~~~powershell
[CmdletBinding(SupportsShouldProcess)]
param([Parameter(Mandatory)][string]$ComputerListPath)
$computers = Import-Csv -LiteralPath $ComputerListPath
foreach ($computer in $computers) {
    try {
        if ($PSCmdlet.ShouldProcess($computer.Name, 'Run remote audit')) {
            Invoke-Command -ComputerName $computer.Name -ScriptBlock { Get-Service | Where-Object Status -EQ 'Running' } -ErrorAction Stop
        }
    } catch { Write-Warning "[$($computer.Name)] $($_.Exception.Message)" }
}
~~~

## 10. PowerShell security

### Principle of least privilege

- Regular users do not need Global Admin or Domain Admin.
- Keep administrative and everyday accounts separate.
- Grant rights through well-designed groups and give scripts only the permissions they need.
- Log and review privilege changes.

### Windows Features

On Windows Server, the ServerManager module provides:

~~~powershell
Get-WindowsFeature
Install-WindowsFeature -Name Web-Server -WhatIf
Uninstall-WindowsFeature -Name Web-Server -WhatIf
~~~

These cmdlets manage **Windows Server** roles and features; they are not a general way to manage user roles.

### Script signing and hardening

~~~powershell
$certificate = Get-ChildItem Cert:\CurrentUser\My -CodeSigningCert | Select-Object -First 1
Set-AuthenticodeSignature -FilePath .\Script.ps1 -Certificate $certificate
Get-AuthenticodeSignature .\Script.ps1
~~~

An organization needs a correctly issued and trusted certificate, a protected private key, and lifecycle/revocation management. A signature proves authorship and integrity after signing; it does not prove that code is safe.

Check the current language mode with `$ExecutionContext.SessionState.LanguageMode`. Constrained Language Mode is effective as part of WDAC/AppLocker, not as a manually set variable in a potentially hostile session. Additional hardening: WDAC/AppLocker, Script Block/Module Logging and Transcription, AMSI and endpoint protection, JEA, protected PowerShell remoting, disabling PowerShell v2, and centralized event collection/alerting. Plan and test policy changes centrally; one script does not replace GPO, MDM, or WDAC.

## 12. Red Team: the role of PowerShell

The course provides only an overview. PowerShell is widely used after initial access for reconnaissance, code execution, privilege escalation, lateral movement, and data collection. PowerShell Empire and PowerSploit are mentioned as historically known post-exploitation/penetration-testing toolsets. The same capabilities make logging and restriction of PowerShell important to Blue Team.

For defense, monitor unusual arguments, encoded commands and policy bypasses; analyze Script Block Logging and the parent-process → PowerShell → network/child-process chain; limit privileges, outbound connections and remote administration; use allowlisting, JEA, EDR and centralized SIEM. Conduct offensive tests only in a lab or an explicitly approved scope. This course does not teach full exploitation.

## 13. REST APIs from PowerShell

The main HTTP methods are `GET` (read a resource), `POST` (create or start an operation), `PUT` (replace a resource), `PATCH` (partially modify it), and `DELETE` (remove it). Exact semantics come from the API documentation.

~~~powershell
$uri = 'https://api.github.com/repos/PowerShell/PowerShell'
$headers = @{ Accept = 'application/vnd.github+json' }
$repository = Invoke-RestMethod -Method Get -Uri $uri -Headers $headers
$repository | Select-Object full_name, stargazers_count, open_issues_count
~~~

`$uri` stores an endpoint, `$headers` is an HTTP-header hashtable, `-Method Get` chooses HTTP GET explicitly, and `Invoke-RestMethod` converts JSON to a PowerShell object. Use HTTPS for real work and never send tokens over HTTP. An ordinary HTTP/HTTPS request does not require running PowerShell as administrator.

For a normal script, `$number = 3` is shorter and clearer than `Set-Variable`; use the latter mainly for dynamically built names or scope/options. `@{ ... }` creates a **hashtable**, not JSON; `ConvertTo-Json` converts it. `@parameters` is splatting: hashtable keys become named command parameters.

~~~powershell
$body = @{ meal = 'pizza'; cook = 'Barbara' }
$parameters = @{ Method='Post'; Uri='https://api.example.test/meals'; ContentType='application/json'; Body=$body | ConvertTo-Json -Depth 5; ErrorAction='Stop' }
try { Invoke-RestMethod @parameters } catch { Write-Error "API request failed: $($_.Exception.Message)" }
~~~

Pass headers as a hashtable; do not convert them to JSON. Never put tokens or passwords in `.ps1`, Git, or terminal history—use SecretManagement, CI/CD secrets, or an approved vault. Authentication may use Bearer tokens, API keys, Basic authentication, OAuth 2.0, client certificates, or cloud managed identities according to the API documentation.

Handle HTTP 2xx/4xx/5xx according to the API documentation, follow pagination links/tokens, and avoid inefficient `$allItems += ...` for very large sets. Do not disable TLS certificate validation. Keep timeouts/retries bounded and do not automatically retry non-idempotent `POST`/`DELETE` operations.

`Invoke-RestMethod` is convenient for JSON/XML APIs and normally returns objects; `Invoke-WebRequest` returns a more general HTTP response when headers, status, HTML, or a file matter.

## 17. Final practical template

This framework combines parameters, input validation, verbose output, error handling, objects, and a safe dry run:

~~~powershell
[CmdletBinding(SupportsShouldProcess)]
param([Parameter(Mandatory)][ValidateScript({ Test-Path -LiteralPath $_ -PathType Leaf })][string]$ComputerListPath, [ValidateRange(1, 10)][int]$Count = 1)
Set-StrictMode -Version Latest
$ErrorActionPreference = 'Stop'
try {
    $computers = Get-Content -LiteralPath $ComputerListPath | Where-Object { -not [string]::IsNullOrWhiteSpace($_) } | Sort-Object -Unique
    foreach ($computer in $computers) {
        if ($PSCmdlet.ShouldProcess($computer, 'Test connectivity')) {
            Write-Verbose "Checking $computer"
            $online = Test-Connection -ComputerName $computer -Count $Count -Quiet -ErrorAction Stop
            [pscustomobject]@{ ComputerName=$computer; Online=$online; CheckedAt=Get-Date }
        }
    }
} catch { Write-Error "Audit failed: $($_.Exception.Message)"; throw }
~~~

Run the safe check as ` .\Audit-Hosts.ps1 -ComputerListPath .\hosts.txt -Verbose -WhatIf`.

## 18. Corrections worth making in the course

- `$name` is a variable, not a “pipe variable”; a pipeline exists only with an explicit `|`.
- Windows `ping` is normally `ping.exe`; the object cmdlet is `Test-Connection`.
- Aliases are useful interactively, but full command names are better in learning and production scripts.
- `RemoteSigned` normally only needs `CurrentUser`; Execution Policy is not a security boundary and is distinct from UAC.
- Do not run PowerShell as administrator by default; elevate only for the concrete operation.
- `catch` does not catch all non-terminating errors without `-ErrorAction Stop`; `continue` skips an iteration.
- `PUT` normally replaces, while `PATCH` commonly makes a partial update. A hashtable is not JSON; headers stay hashtables and must not contain a plaintext password.
- The .NET Interactive/Polyglot Notebooks VS Code extension shown in the lesson was discontinued in 2026.
- Study PowerShell Empire/PowerSploit only in an authorized lab; for modern defense, telemetry, allowlisting, JEA, and least privilege matter more.

### Minimum checklist before running an unknown `.ps1`

- [ ] The source and author have been verified.
- [ ] The whole codebase, invoked files, and modules have been read.
- [ ] URLs, network destinations, deletion commands, and permission changes have been checked.
- [ ] There is no obfuscation, `EncodedCommand`, or download-and-immediate-execution behavior.
- [ ] A published SHA-256/signature has been compared where available.
- [ ] PSScriptAnalyzer shows no critical issues.
- [ ] The first run is non-administrative, in a disposable VM, with test data.
- [ ] `-WhatIf`/`-Confirm` is used where supported.
- [ ] A log, backup, and rollback plan exist.
- [ ] Secrets are not written to code, arguments, transcripts, or Git.
