## 1. Быстрый старт

### Что такое PowerShell

PowerShell сочетает командную оболочку и язык сценариев. Команды обычно возвращают не простой текст, а .NET-объекты. Это позволяет передавать объекты по конвейеру и обращаться к их свойствам без ручного разбора строк.

Полные имена командлетов строятся по схеме Глагол-Существительное:

~~~powershell
Get-Process
Get-Service
Set-ExecutionPolicy
Invoke-RestMethod
~~~

Правильный термин — **cmdlet / командлет**. Windows PowerShell 5.1 встроен в современные версии Windows; PowerShell 7 — отдельный кроссплатформенный продукт, который при необходимости устанавливается отдельно.

### Как читать команду PowerShell

Разберём строку по частям:

~~~powershell
Get-Process -Name 'powershell' -ErrorAction SilentlyContinue
~~~

- Get-Process — имя командлета: глагол Get означает «получить», существительное Process — «процесс».
- -Name — именованный параметр.
- 'powershell' — значение параметра Name.
- -ErrorAction — общий параметр, определяющий поведение при незавершающей ошибке.
- SilentlyContinue — значение ErrorAction: не показывать ошибку и продолжить. В реальных сценариях не используйте его без причины.

Узнать синтаксис и наборы параметров:

~~~powershell
Get-Command Get-Process -Syntax
Get-Help Get-Process -Parameter Name
Get-Help about_CommonParameters
~~~

Параметры лучше писать по имени. Позиционный вариант короче, но менее очевиден:

~~~powershell
Get-Process -Name 'powershell'  # понятно
Get-Process 'powershell'        # работает позиционно, но смысл менее явный
~~~

Switch-параметр — переключатель без отдельного значения:

~~~powershell
Get-ChildItem -Recurse -Force
~~~

Здесь -Recurse включает обход подпапок, а -Force показывает скрытые элементы.

### Основные знаки синтаксиса

| Запись | Что означает |
|---|---|
| $name | переменная |
| -Name | параметр команды |
| 'text' | строка без подстановки переменных |
| "text $name" | строка с подстановкой переменной |
| $(...) | вычислить выражение внутри строки или другого выражения |
| (...) | сгруппировать выражение или сначала получить результат команды |
| {...} | блок кода: тело функции, цикла, условия или ScriptBlock |
| @() | гарантированно создать массив |
| @{ Key = Value } | создать hashtable — набор ключ/значение |
| [type] | указать или проверить тип |
| .Property | обратиться к свойству объекта |
| .Method() | вызвать метод объекта |
| \| | передать объекты следующей команде |
| & | оператор вызова: выполнить команду/сценарий, путь к которому является выражением |
| # | однострочный комментарий |
| <# ... #> | многострочный комментарий или comment-based help |

Пример, объединяющий несколько конструкций:

~~~powershell
$serviceName = 'WinRM'
$service = Get-Service -Name $serviceName

if ($service.Status -eq 'Running') {
    "Service $($service.Name) is running"
}
~~~

Точка в $service.Status обращается к свойству Status. Конструкция $($service.Name) нужна, чтобы внутри двойной строки вычислить более сложное выражение, чем простая переменная.

### Переменные и типы данных

Переменная создаётся присваиванием:

~~~powershell
$name = 'server01'
$count = 3
$enabled = $true
$checkedAt = Get-Date
~~~

Посмотреть тип:

~~~powershell
$name.GetType().FullName
$count.GetType().FullName
$checkedAt.GetType().FullName
~~~

Тип можно задать явно:

~~~powershell
[string]$computerName = 'server01'
[int]$retryCount = 3
[bool]$enabled = $true
[datetime]$deadline = '2026-08-20'
~~~

Часто встречающиеся типы:

| Тип | Пример | Назначение |
|---|---|---|
| [string] | 'server01' | текст |
| [int] | 42 | целое число |
| [double] | 3.14 | число с дробной частью |
| [bool] | $true / $false | логическое значение |
| [datetime] | Get-Date | дата и время |
| [array] / [object[]] | 1, 2, 3 | упорядоченная коллекция |
| [hashtable] | @{ Name = 'srv01' } | пары ключ/значение |
| [pscustomobject] | [pscustomobject]@{...} | объект с именованными свойствами |

PowerShell часто преобразует тип автоматически, но лучше не полагаться на неоднозначные преобразования:

~~~powershell
'10' + '2'        # '102': склеивание строк
[int]'10' + 2     # 12: сложение чисел
~~~

### Строки: одинарные и двойные кавычки

~~~powershell
$name = 'server01'

'Computer: $name'             # Computer: $name
"Computer: $name"             # Computer: server01
"Length: $($name.Length)"     # Length: 8
~~~

Одинарные кавычки сохраняют текст буквально. Двойные подставляют переменные и подвыражения.

Для многострочного текста:

~~~powershell
$message = @'
Переменные $name здесь не раскрываются.
Это literal here-string.
'@

$expanded = @"
Computer: $name
Checked: $(Get-Date)
"@
~~~

### Массивы

~~~powershell
$computers = 'server01', 'server02', 'server03'

$computers[0]       # первый элемент
$computers[-1]      # последний элемент
$computers.Count    # количество элементов
$computers += 'server04'

foreach ($computer in $computers) {
    $computer
}
~~~

Оператор диапазона:

~~~powershell
1..5        # 1, 2, 3, 4, 5
5..1        # 5, 4, 3, 2, 1
~~~

@(...) гарантирует массив даже при нуле или одном результате:

~~~powershell
$services = @(Get-Service -Name 'WinRM')
$services.Count
~~~

### Hashtable и PSCustomObject

Hashtable удобна для настроек и параметров:

~~~powershell
$settings = @{
    ComputerName = 'server01'
    Count        = 1
    Quiet        = $true
}

$settings['ComputerName']
$settings.ComputerName

Test-Connection @settings
~~~

В последней строке @settings означает **splatting**: ключи hashtable становятся именами параметров, а значения — их аргументами.

PSCustomObject удобен для результата, который пойдёт в pipeline или CSV:

~~~powershell
$result = [pscustomobject]@{
    ComputerName = 'server01'
    Online       = $true
    CheckedAt    = Get-Date
}

$result.Online
$result | Format-List
$result | Export-Csv .\result.csv -NoTypeInformation
~~~

### $null, $true и $false

$null означает отсутствие значения:

~~~powershell
$value = $null

if ($null -eq $value) {
    'Value is absent'
}
~~~

Ставить $null слева — полезная привычка: если справа окажется коллекция, сравнение останется однозначным.

В условии PowerShell преобразует значение в Boolean. Упрощённо:

- $false и $null — ложь;
- число 0 — ложь, остальные числа — истина;
- пустая строка — ложь, непустая — истина;
- пустая коллекция — ложь; коллекция с элементами обычно истина.

Явное сравнение часто понятнее:

~~~powershell
if ($service.Status -eq 'Running') { ... }  # лучше, чем надеяться на truthiness объекта
~~~

### Как находить команды и справку

~~~powershell
# Найти команды по существительному или шаблону
Get-Command -Noun Process
Get-Command -Name '*Service*'

# Прочитать справку
Get-Help Get-Process
Get-Help Get-Process -Examples
Get-Help Get-Process -Full
Get-Help Get-Process -Online

# Обновить локальную справку (иногда нужны повышенные права)
Update-Help

# Список псевдонимов и расшифровка конкретного псевдонима
Get-Alias
Get-Alias pwd
Get-Alias ls
Get-Alias -Name 'g*'

# Найти псевдонимы команд CSV
Get-Alias | Where-Object Definition -Like '*Csv*'
~~~

Псевдонимы удобны интерактивно, но в сохраняемых сценариях лучше использовать полные имена: Get-ChildItem, а не ls; Get-Location, а не pwd. Такой код легче читать и переносить.

### Навигация и базовые команды

~~~powershell
Get-Location                 # текущая папка; псевдоним pwd
Get-ChildItem                # содержимое папки; псевдонимы ls, dir
Set-Location C:\Users        # перейти в папку; псевдоним cd
Set-Location ..              # на уровень выше
Clear-Host                   # очистить экран; псевдоним clear
Get-Process                  # процессы; псевдонимы gps, ps
~~~

### Конвейер объектов

Символ | передаёт результат одной команды следующей:

~~~powershell
Get-Process |
    Where-Object CPU -GT 10 |
    Sort-Object CPU -Descending |
    Select-Object -First 10 Name, Id, CPU
~~~

Полезно сначала изучить тип и доступные свойства объекта:

~~~powershell
Get-Process | Get-Member
Get-Service | Select-Object -First 5 | Format-Table Name, Status, StartType
~~~

Format-Table и Format-List предназначены для финального отображения. Не помещайте их в середину конвейера, если дальше нужно обрабатывать объекты.

### Как pipeline обрабатывает объекты

~~~powershell
Get-Process |
    Where-Object { $_.CPU -gt 10 } |
    Select-Object Name, Id, CPU |
    Export-Csv .\processes.csv -NoTypeInformation
~~~

Пошагово:

1. Get-Process создаёт объекты процессов.
2. Символ | передаёт их по одному в Where-Object.
3. Внутри блока { ... } автоматическая переменная $_ обозначает текущий объект.
4. Условие $_.CPU -gt 10 оставляет только процессы, у которых CPU больше 10.
5. Select-Object формирует объекты только со свойствами Name, Id и CPU.
6. Export-Csv сериализует эти свойства в CSV.

$_ и $PSItem — два имени одной автоматической переменной:

~~~powershell
Get-Service | Where-Object { $_.Status -eq 'Running' }
Get-Service | Where-Object { $PSItem.Status -eq 'Running' }
~~~

Короткая форма Where-Object подходит для простого сравнения одного свойства:

~~~powershell
Get-Service | Where-Object Status -eq 'Running'
~~~

ForEach-Object преобразует каждый объект pipeline:

~~~powershell
Get-Service | ForEach-Object {
    [pscustomobject]@{
        Name        = $_.Name
        DisplayName = $_.DisplayName
        Running     = $_.Status -eq 'Running'
    }
}
~~~

Не путайте:

- foreach ($item in $items) — языковая конструкция; коллекция обычно уже находится в памяти;
- ForEach-Object { ... } — командлет pipeline; обрабатывает входящие объекты по мере поступления.

Pipeline связывает команды через параметры, принимающие pipeline input. Привязка бывает:

- **ByValue** — тип входного объекта подходит параметру;
- **ByPropertyName** — имя свойства входного объекта совпадает с именем параметра.

Проверить это можно в полной справке:

~~~powershell
Get-Help Stop-Service -Full
~~~

Пример привязки по имени свойства с безопасной имитацией:

~~~powershell
[pscustomobject]@{ Name = 'Spooler' } |
    Stop-Service -WhatIf
~~~

Свойство Name передаётся параметру -Name. Именно поэтому правильные имена свойств важны в объектах PowerShell.

## 2. Как читать существующие сценарии

Сценарии PowerShell имеют расширение .ps1. При разборе чужого кода удобно двигаться сверху вниз:

1. Прочитать комментарии справки: .SYNOPSIS, .DESCRIPTION, .PARAMETER, .EXAMPLE.
2. Найти блок param(...) и понять входные данные и обязательные параметры.
3. Выписать переменные — они начинаются с $.
4. Найти функции, циклы, условия и точки удалённого выполнения.
5. Для незнакомых команд вызвать Get-Help и Get-Command.
6. Проверить внешние адреса, файлы, модули, права и возможные побочные эффекты.
7. Запустить статический анализ и тестировать без прав администратора в изолированной среде.

Минимальный документированный сценарий:

~~~powershell
<#
.SYNOPSIS
Проверяет доступность узлов из текстового файла.

.PARAMETER Path
Путь к файлу, содержащему по одному имени или IP-адресу в строке.

.EXAMPLE
.\Test-Hosts.ps1 -Path .\hosts.txt
#>

[CmdletBinding()]
param(
    [Parameter(Mandatory)]
    [ValidateScript({ Test-Path -LiteralPath $_ -PathType Leaf })]
    [string]$Path
)

$computers = Get-Content -LiteralPath $Path

foreach ($computer in $computers) {
    $online = Test-Connection -ComputerName $computer -Count 1 -Quiet

    [pscustomobject]@{
        ComputerName = $computer
        Online       = $online
        CheckedAt    = Get-Date
    }
}
~~~

В уроке разобраны сценарии добавления удалённого принтера и пакетной проверки адресов. Упомянутые команды:

~~~powershell
Get-Help Write-Verbose
Get-Help Invoke-Command
Get-Help Add-PrinterPort
Get-Help Write-Host

Get-Content .\ip-addresses.txt
Start-Transcript -Path .\batch-ping.log
Test-Connection -ComputerName server01 -Count 1
Stop-Transcript
~~~

Write-Verbose подходит для диагностических сообщений внутри advanced script/function; пользователь включает их параметром -Verbose. Для данных лучше возвращать объекты, а не печатать строки через Write-Host.

### Разбор Add-RemotePrinter.ps1 из урока

Преподаватель открывает [Add-RemotePrinter.ps1](https://github.com/zweilosec/PowerShell-Administration-Tools/blob/master/Add-RemotePrinter.ps1). Его полезно читать по слоям:

1. **Comment-based help** описывает назначение, входы и примеры.
2. **Param** объявляет ComputerName, DomainName, UserName, адрес принтера, драйвер, отображаемое имя и имя порта.
3. **Begin** вычисляет общие значения перед обработкой входных объектов.
4. **Process** перебирает компьютеры, создаёт PSSession и вызывает команды на удалённой машине.
5. **End** выводит итоговый счётчик.

Значение важных атрибутов:

~~~powershell
[CmdletBinding()]
param(
    [Parameter(Mandatory, ValueFromPipeline)]
    [Alias('Name')]
    [string[]]$ComputerName
)
~~~

- [CmdletBinding()] превращает сценарий/функцию в advanced command и добавляет общие параметры вроде -Verbose и -ErrorAction.
- Mandatory требует значение.
- ValueFromPipeline разрешает принимать объекты из pipeline.
- [Alias('Name')] помогает привязке, когда входной объект имеет свойство Name.
- [string[]] означает «одна или несколько строк».

Begin/Process/End:

~~~powershell
begin {
    # Выполняется один раз до первого входного объекта.
}
process {
    # Выполняется для входящих объектов pipeline.
}
end {
    # Выполняется один раз после обработки.
}
~~~

Скелет безопасного изучения удалённой операции:

~~~powershell
[CmdletBinding(SupportsShouldProcess)]
param(
    [Parameter(Mandatory)]
    [string[]]$ComputerName,

    [Parameter(Mandatory)]
    [pscredential]$Credential,

    [Parameter(Mandatory)]
    [string]$PrinterHostAddress,

    [Parameter(Mandatory)]
    [string]$WindowsDisplayName,

    [Parameter(Mandatory)]
    [string]$DriverName,

    [string]$PortName = $PrinterHostAddress
)

foreach ($computer in $ComputerName) {
    $session = $null
    try {
        $session = New-PSSession -ComputerName $computer -Credential $Credential -ErrorAction Stop

        if ($PSCmdlet.ShouldProcess($computer, "Add printer $WindowsDisplayName")) {
            $remoteParameters = @{
                Session      = $session
                ArgumentList = $PortName, $PrinterHostAddress, $DriverName, $WindowsDisplayName
                ErrorAction  = 'Stop'
                ScriptBlock  = {
                    param($RemotePort, $RemoteAddress, $RemoteDriver, $RemoteDisplayName)

                    # -WhatIf оставлен специально: изменения только показываются.
                    Add-PrinterPort -Name $RemotePort -PrinterHostAddress $RemoteAddress -WhatIf
                    Add-PrinterDriver -Name $RemoteDriver -WhatIf
                    Add-Printer -Name $RemoteDisplayName -PortName $RemotePort -DriverName $RemoteDriver -WhatIf
                }
            }
            Invoke-Command @remoteParameters
        }
    }
    catch {
        Write-Warning "[$computer] $($_.Exception.Message)"
    }
    finally {
        if ($null -ne $session) {
            Remove-PSSession -Session $session
        }
    }
}
~~~

Зачем ArgumentList и param внутри ScriptBlock: удалённая сессия не видит локальные переменные автоматически. Значения нужно передать явно либо использовать область $using:.

Исходный GitHub-сценарий полезен как материал для чтения, но не как готовый production-код. В текущей версии есть проблемы:

- для значения порта используется несуществующая переменная $PrinterIP вместо $PrinterHostAddress;
- удалённый ScriptBlock обращается к локальным переменным без ArgumentList или $using:;
- написано Print-Verbose вместо Write-Verbose;
- созданную сессию надёжнее удалять через Remove-PSSession -Session $session;
- ParameterSetName распределён так, что комбинация обязательных параметров может конфликтовать;
- нет try/finally, поэтому при ошибке PSSession может остаться открытой.

### Разбор BatchPing.ps1

В видео описана версия со Start-Transcript/Stop-Transcript. В текущем [BatchPing.ps1](https://github.com/TDGalvin/PowerShell-Batch-Ping-Script/blob/main/BatchPing.ps1) результат уже сохраняется через Export-Csv.

Логика:

1. Get-Content читает IP-адреса/имена из IPAddresses.txt.
2. ForEach-Object выполняет блок для каждой строки; текущая строка доступна как $_.
3. Test-Connection -Count 1 -Quiet возвращает $true или $false.
4. Для каждого адреса создаётся объект с двумя свойствами.
5. Export-Csv пишет все объекты в BatchPingLog.csv.

Более понятная версия:

~~~powershell
$results = Get-Content -LiteralPath .\IPAddresses.txt |
    Where-Object { -not [string]::IsNullOrWhiteSpace($_) } |
    ForEach-Object {
        $computer = $_.Trim()

        try {
            $testParameters = @{
                ComputerName = $computer
                Count        = 1
                Quiet        = $true
                ErrorAction  = 'Stop'
            }
            $online = Test-Connection @testParameters

            [pscustomobject]@{
                ComputerName = $computer
                Online       = $online
                Error        = $null
            }
        }
        catch {
            [pscustomobject]@{
                ComputerName = $computer
                Online       = $false
                Error        = $_.Exception.Message
            }
        }
    }

$results | Export-Csv -LiteralPath .\BatchPingLog.csv -NoTypeInformation
~~~

Не путайте два разных результата:

- доступный узел → Online = $true;
- узел не отвечает → обычно Online = $false, это не обязательно exception;
- неверное имя/DNS или системная ошибка → попадает в catch благодаря -ErrorAction Stop.

NoTypeInformation запрещает добавлять в первую строку CSV служебное имя .NET-типа.

## 3. Функции

Функции позволяют переиспользовать код. Простейший вариант:

~~~powershell
function Show-PowerShellInfo {
    $PSVersionTable.PSVersion
    Get-Location
}

Show-PowerShellInfo
~~~

Практичный advanced function:

~~~powershell
function Test-HostOnline {
    [CmdletBinding()]
    param(
        [Parameter(Mandatory, ValueFromPipeline)]
        [ValidateNotNullOrEmpty()]
        [string[]]$ComputerName
    )

    process {
        foreach ($computer in $ComputerName) {
            [pscustomobject]@{
                ComputerName = $computer
                Online       = Test-Connection -ComputerName $computer -Count 1 -Quiet
            }
        }
    }
}

'server01', 'server02' | Test-HostOnline
~~~

Как работает эта функция:

- [CmdletBinding()] добавляет общие параметры -Verbose, -Debug, -ErrorAction, -WarningAction и другие;
- param(...) содержит контракт функции;
- [string[]] разрешает одну строку или массив строк;
- ValueFromPipeline разрешает передавать строки через |;
- process выполняется для элементов, поступающих из pipeline;
- [pscustomobject] возвращает структурированный результат.

Switch-параметр:

~~~powershell
function Get-Greeting {
    param(
        [Parameter(Mandatory)]
        [string]$Name,

        [switch]$UpperCase
    )

    $message = "Hello, $Name"
    if ($UpperCase) {
        $message = $message.ToUpperInvariant()
    }

    $message
}

Get-Greeting -Name 'Alice'
Get-Greeting -Name 'Alice' -UpperCase
~~~

Проверка входных значений:

~~~powershell
param(
    [ValidateNotNullOrEmpty()]
    [string]$ComputerName,

    [ValidateRange(1, 10)]
    [int]$Count = 1,

    [ValidateSet('Info', 'Warning', 'Error')]
    [string]$Level = 'Info'
)
~~~

PowerShell возвращает из функции весь обычный success output, а не только значение после return:

~~~powershell
function Get-Demo {
    'first'
    'second'
}

$result = Get-Demo
$result.Count       # 2
~~~

return завершает текущую функцию/script block и при наличии выражения отправляет его в output:

~~~powershell
function Get-SafeRatio {
    param([double]$A, [double]$B)

    if ($B -eq 0) {
        return $null
    }

    $A / $B
}
~~~

Write-Host не является обычным возвращаемым объектом. Для результата функции пишите объект напрямую или используйте Write-Output; для интерфейсного сообщения — Write-Host; для диагностики — Write-Verbose.

Рекомендации:

- называйте функции в форме ApprovedVerb-Noun; список глаголов покажет Get-Verb;
- объявляйте входы в param(...) и задавайте типы;
- возвращайте объекты, а не форматированный текст;
- используйте Write-Verbose, Write-Warning и Write-Error по назначению;
- не требуйте административных прав без необходимости.

### Запуск .ps1

~~~powershell

# По полному пути; оператор вызова & нужен, когда путь хранится в строке

# Передача параметров

~~~

## 4. Execution Policy и безопасный запуск

Проверка политик по областям:

~~~powershell
Get-ExecutionPolicy -List
~~~

PowerShell определяет семь значений политики:

| Политика | Смысл |
|---|---|
| AllSigned | Все сценарии и конфигурационные файлы PowerShell должны быть подписаны доверенным издателем. |
| RemoteSigned | Локальные сценарии могут быть неподписанными; загруженные из интернета требуют подписи либо осознанного Unblock-File. |
| Restricted | Интерактивные команды разрешены, сценарии и модули-скрипты не выполняются. |
| Unrestricted | Неподписанные сценарии выполняются; для файлов из внешней зоны Windows возможно предупреждение. |
| Bypass | PowerShell ничего не блокирует и не показывает предупреждений. |
| Undefined | В данном scope политика не задана; это нормальное состояние, а не уязвимость само по себе. |
| Default | Восстанавливает политику по умолчанию для продукта. |

Scope в порядке приоритета: MachinePolicy, UserPolicy, Process, CurrentUser, LocalMachine. Политика, заданная GPO, может переопределить локальную настройку.

Для учебного компьютера безопаснее менять только политику текущего пользователя:

~~~powershell
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
~~~

Если доверенный загруженный файл помечен как полученный из интернета:

~~~powershell
Get-FileHash .\TrustedScript.ps1 -Algorithm SHA256
Unblock-File .\TrustedScript.ps1
~~~

Ключевые оговорки:

- Execution Policy — защита от случайного запуска, а не полноценная граница безопасности.
- Не меняйте LocalMachine, если достаточно CurrentUser или Process.
- Не используйте Bypass как постоянную настройку.
- Сначала прочитайте код, проверьте источник и хеш, затем запускайте без повышения прав.
- Для непроверенного кода используйте одноразовую VM/Windows Sandbox.
- На non-Windows Get-ExecutionPolicy сообщает Unrestricted, но механизм зон Windows там не применяется и поведение фактически ближе к Bypass.

Важные исправления к уроку о собеседованиях:

- Undefined означает, что в конкретном scope значение отсутствует; эффективная политика вычисляется из остальных scope и системного значения по умолчанию.
- UAC-диалог «разрешить приложению вносить изменения» появляется из-за повышения прав, а не из-за Execution Policy.
- AllSigned относится к PowerShell-сценариям и конфигурационным файлам, а не определяет возможность запуска Adobe, Word или других обычных приложений.
- Execution Policy работает только в Windows и не должна преподноситься как защита от целенаправленного злоумышленника.

## 5. Git и контроль версий

Git хранит историю изменений; GitHub — сервис размещения Git-репозиториев и совместной работы.

Ментальная модель Git:

~~~text
working directory → staging area → local commit → remote repository
      git add          git commit         git push
~~~

- **Working directory** — файлы, которые вы редактируете.
- **Staging area / index** — изменения, выбранные для следующего commit.
- **Commit** — сохранённый снимок выбранных изменений с сообщением.
- **Branch** — подвижное имя линии разработки.
- **Remote** — ссылка на удалённый репозиторий; обычно origin.
- **Push** отправляет локальные commits на remote.
- **Pull** получает удалённые изменения и интегрирует их в текущую ветку.
- **Merge** объединяет линии истории.
- **Rebase** переносит локальные commits на новую базу и переписывает их идентификаторы.

Базовый цикл:

~~~powershell
git init
git status
git add .
git commit -m "Add initial PowerShell script"

git branch --show-current
git switch -c feature/logging

git remote add origin https://github.com/ORG/REPO.git
git push -u origin feature/logging
git pull --rebase
~~~

Пошагово для существующего проекта:

~~~powershell
git clone https://github.com/ORG/REPO.git
Set-Location .\REPO

git status
git switch -c fix/error-handling

# Отредактировать файлы
git diff
git add .\Script.ps1
git diff --staged
git commit -m "Handle non-terminating errors"
git push -u origin fix/error-handling
~~~

Что означает:

- clone — получить репозиторий вместе с историей;
- status — показать ветку и незакоммиченные изменения;
- switch -c — создать ветку и перейти в неё;
- diff — увидеть изменения, ещё не добавленные в staging;
- add — выбрать изменение для commit;
- diff --staged — проверить будущий commit;
- commit — записать снимок локально;
- push -u — впервые отправить ветку и связать её с remote-веткой.

Merge conflict означает, что Git не может автоматически выбрать между несовместимыми изменениями. Нужно открыть отмеченные файлы, осознанно собрать правильную версию, протестировать, затем добавить исправленные файлы и завершить commit/rebase.

Полезный минимум:

~~~powershell
git log --oneline --decorate --graph --all
git diff
git diff --staged
git restore --staged .\file.ps1
~~~

Перед публикацией проверьте, что в истории и файлах нет паролей, токенов, закрытых ключей, внутренних адресов и персональных данных. Секреты нельзя хранить в Git даже в удалённой ветке: они остаются в истории.

### Как работать со сценарием в VS Code

1. Откройте именно папку проекта, а не один случайный файл.
2. Создайте файл с расширением .ps1.
3. Убедитесь, что выбран правильный PowerShell session/version.
4. Запускайте выделение или весь файл во встроенном терминале.
5. Просматривайте Problems и предупреждения анализатора.
6. Поставьте breakpoint на строке, где нужно остановиться.
7. Запустите debug и проверяйте Variables, Watch, Call Stack.
8. Используйте Step Over, Step Into и Step Out.
9. После исправления повторите тест на нормальном и ошибочном входе.

Breakpoint останавливает код **до** выполнения строки. Это позволяет увидеть текущие значения:

~~~powershell
$numbers = 1..5

foreach ($number in $numbers) {
    $square = $number * $number  # удобная строка для breakpoint

}
~~~

- Step Over выполняет текущую строку, не заходя внутрь вызванной функции.
- Step Into заходит внутрь функции.
- Step Out завершает текущую функцию и возвращается к вызывающему коду.
- Continue работает до следующего breakpoint или завершения.

Не отлаживайте непроверенный сценарий от администратора: debugger всё равно выполняет его код.

## 7. Управление потоком выполнения

### Условие if / elseif / else

~~~powershell
$freeSpaceGB = 12

if ($freeSpaceGB -lt 5) {
    'Critical'
}
elseif ($freeSpaceGB -lt 20) {
    'Warning'
}
else {
    'OK'
}
~~~

PowerShell проверяет условия сверху вниз. Выполняется первый подходящий блок, остальные пропускаются.

Несколько условий:

~~~powershell
$enabled = $true
$role = 'Analyst'

if ($enabled -and ($role -eq 'Analyst')) {
    'Access condition passed'
}
~~~

Скобки показывают порядок вычисления. Это особенно важно, когда вместе используются -and и -or.

### foreach

~~~powershell
$websites = 'google.com', 'microsoft.com', 'example.org'

foreach ($site in $websites) {
    $online = Test-Connection -ComputerName $site -Count 1 -Quiet
    "{0}: {1}" -f $site, $(if ($online) { 'online' } else { 'unreachable' })
}
~~~

В уроке используется слово ping, однако в Windows это обычно внешняя программа ping.exe, а не командлет. Для сценариев предпочтительнее Test-Connection, потому что он возвращает объекты и поддерживает параметры PowerShell.

### Классический for

~~~powershell
for ($number = 0; $number -le 25; $number++) {
    "Number is $number"
}
~~~

### while, do...while, do...until

~~~powershell
$attempt = 0
while ($attempt -lt 3) {
    $attempt++
    "Attempt $attempt"
}

do {
    $value = Read-Host 'Enter q to quit'
} while ($value -ne 'q')

do {
    $value = Read-Host 'Enter READY'
} until ($value -eq 'READY')
~~~

В отличие от while, циклы do... выполняют тело хотя бы один раз.

Игра угадывания из урока в законченном виде:

~~~powershell
$number = Get-Random -Minimum 1 -Maximum 6

do {
    [int]$guess = Read-Host 'Guess a number from 1 to 5'

    if ($guess -lt $number) {
        'Too low'
    }
    elseif ($guess -gt $number) {
        'Too high'
    }
} until ($guess -eq $number)

'Correct'
~~~

- Get-Random -Minimum 1 -Maximum 6 возвращает целое от 1 до 5: верхняя граница не включается.
- Read-Host возвращает строку, поэтому [int] преобразует ввод в число.
- -lt означает «меньше», -gt — «больше», -eq — «равно».
- do гарантирует хотя бы одну попытку.
- until повторяет блок, пока условие **не станет истинным**.

При production-вводе преобразование [int] может выбросить ошибку. Безопаснее использовать TryParse:

~~~powershell
$parsed = 0
$valid = [int]::TryParse((Read-Host 'Enter a number'), [ref]$parsed)

if (-not $valid) {
    Write-Warning 'Not a valid integer'
}
~~~

### break, continue, return

~~~powershell
foreach ($item in 1..10) {
    if ($item -eq 3) { continue } # пропустить текущую итерацию
    if ($item -gt 7) { break }    # выйти из цикла
    $item
}

function Get-FirstEvenNumber {
    param([int[]]$Numbers)

    foreach ($number in $Numbers) {
        if ($number % 2 -eq 0) {
            return $number        # выйти из функции и вернуть значение
        }
    }
}
~~~

continue не является «противоположностью» break: он переходит к следующей итерации, а break завершает цикл. return обычно завершает функцию или script block, а не просто цикл.

### Операторы сравнения

Операторы сравнения возвращают $true/$false для одиночного значения и могут фильтровать коллекцию, если коллекция находится слева.

#### Равенство и порядок

| Оператор | Английское название | Смысл | Пример | Результат |
|---|---|---|---|---|
| -eq | equal | равно | 5 -eq 5 | $true |
| -ne | not equal | не равно | 5 -ne 3 | $true |
| -gt | greater than | больше | 10 -gt 3 | $true |
| -ge | greater or equal | больше или равно | 10 -ge 10 | $true |
| -lt | less than | меньше | 2 -lt 5 | $true |
| -le | less or equal | меньше или равно | 5 -le 5 | $true |

Примеры в условиях:

~~~powershell
$age = 20

if ($age -ge 18) {
    'Adult'
}

$cpu = 75
if ($cpu -gt 90) {
    'Critical'
}
elseif ($cpu -gt 70) {
    'High'
}
else {
    'Normal'
}
~~~

PowerShell использует -eq, а не =, потому что:

- = присваивает значение: $x = 5;
- -eq сравнивает: $x -eq 5.

По умолчанию строки сравниваются без учёта регистра:

~~~powershell
'Admin' -eq 'admin'     # $true
'Admin' -ceq 'admin'    # $false: c = case-sensitive
'Admin' -ieq 'admin'    # $true: i = явно case-insensitive
~~~

Префиксы c и i работают и с другими строковыми операторами: -cne, -clike, -cmatch, -ilike и т. д.

Следите за типами:

~~~powershell
10 -gt 2              # числовое сравнение: $true
'10' -gt '2'          # строковое сравнение: результат определяется сравнением строк
[int]'10' -gt 2       # явно числовое сравнение
~~~

#### Wildcard: -like и -notlike

-like сравнивает с wildcard-шаблоном:

| Символ | Значение |
|---|---|
| * | любое количество любых символов |
| ? | ровно один любой символ |
| [abc] | один символ из набора |
| [a-z] | один символ из диапазона |

~~~powershell
'server01' -like 'server*'      # $true
'server01' -like 'server??'     # $true
'server01' -notlike 'client*'   # $true

Get-Service -Name 'Win*'
Get-ChildItem -Filter '*.ps1'
~~~

#### Регулярные выражения: -match, -notmatch и -replace

-match использует regex, а не wildcard:

~~~powershell
'server-042' -match '^server-\d{3}$'    # $true
'admin@example.com' -match '@'          # $true
'server01' -notmatch '^client'          # $true
~~~

После успешного -match для одиночной строки группы доступны в $Matches:

~~~powershell
if ('server-042' -match '^([a-z]+)-(\d+)$') {
    $Matches[0]   # server-042 — всё совпадение
    $Matches[1]   # server
    $Matches[2]   # 042
}
~~~

Замена по regex:

~~~powershell
'user@example.com' -replace '@.*$', '@redacted'
# user@redacted
~~~

#### Коллекции: -contains, -in, -notcontains, -notin

Направление имеет значение:

~~~powershell
$roles = 'User', 'Analyst', 'Admin'

$roles -contains 'Admin'       # коллекция содержит значение
'Admin' -in $roles             # значение находится в коллекции
$roles -notcontains 'Guest'
'Guest' -notin $roles
~~~

-contains ожидает коллекцию слева. -in часто легче читается в if:

~~~powershell
if ($currentRole -in 'Analyst', 'Admin') {
    'Allowed'
}
~~~

#### Сравнение коллекции обычным оператором

Если слева коллекция, -eq и другие обычные операторы возвращают совпавшие элементы, а не Boolean:

~~~powershell
$numbers = 1, 2, 3, 4, 5
$numbers -gt 3       # возвращает 4 и 5
$numbers -eq 3       # возвращает 3
~~~

Чтобы проверить наличие элемента с Boolean-результатом, используйте -contains/-in.

#### Проверка типа: -is и -isnot

~~~powershell
42 -is [int]                # $true
'42' -is [string]           # $true
(Get-Date) -is [datetime]   # $true
'42' -isnot [int]           # $true
~~~

#### Логические операторы

| Оператор | Когда $true |
|---|---|
| -and | оба условия истинны |
| -or | хотя бы одно условие истинно |
| -xor | истинно ровно одно из двух условий |
| -not или ! | инвертирует условие |

~~~powershell
($age -ge 18) -and ($enabled -eq $true)
($role -eq 'Admin') -or ($role -eq 'Analyst')
($a -eq $true) -xor ($b -eq $true)
-not (Test-Path .\missing.txt)
!(Test-Path .\missing.txt)
~~~

-and и -or используют short-circuit:

- при $false слева от -and правая часть не вычисляется;
- при $true слева от -or правая часть не вычисляется.

Это позволяет безопасно сначала проверять наличие объекта:

~~~powershell
if (($null -ne $service) -and ($service.Status -eq 'Running')) {
    'Running'
}
~~~

#### Арифметика и присваивание

| Оператор | Значение |
|---|---|
| + | сложение или склеивание |
| - | вычитание |
| * | умножение |
| / | деление |
| % | остаток от деления |
| ++ / -- | увеличить/уменьшить на 1 |
| += / -= / *= / /= / %= | выполнить операцию и присвоить результат |

~~~powershell
$number = 5
$number++       # 6
$number += 4    # 10

10 % 2          # 0 — число чётное
11 % 2          # 1 — число нечётное

$text = 'Power'
$text += 'Shell' # PowerShell
~~~

Именно выражение $number % 2 -eq 0 в примере с return означает «остаток от деления на 2 равен нулю», то есть число чётное.

#### Порядок операторов

Не полагайтесь на память в сложном выражении — используйте скобки:

~~~powershell
if (($cpu -gt 80) -and (($status -eq 'Running') -or $force)) {
    ...
}
~~~

Для встроенной полной справки:

~~~powershell
Get-Help about_Comparison_Operators
Get-Help about_Logical_Operators
Get-Help about_Arithmetic_Operators
Get-Help about_Operator_Precedence
~~~

## 8. Обработка ошибок

try/catch/finally обрабатывает завершающие ошибки. Многие командлеты по умолчанию создают незавершающую ошибку, поэтому для надёжного catch добавляйте -ErrorAction Stop.

~~~powershell
try {
    $service = Get-Service -Name 'DefinitelyMissing' -ErrorAction Stop
    $service
}
catch [Microsoft.PowerShell.Commands.ServiceCommandException] {
    Write-Warning "Service not found: $($_.Exception.Message)"
}
catch {
    Write-Error "Unexpected error: $($_.Exception.Message)"
}
finally {
    Write-Verbose 'Cleanup complete'
}
~~~

Полезные объекты и настройки:

~~~powershell
$Error[0]                       # последняя запись об ошибке
$_.Exception.Message            # сообщение внутри catch
$PSItem.InvocationInfo          # место возникновения
$ErrorActionPreference          # глобальная настройка текущей сессии
~~~

Не ставьте $ErrorActionPreference = 'SilentlyContinue' на весь сценарий: это скрывает проблемы. Обрабатывайте ожидаемые ошибки локально.

### Потоки вывода PowerShell

PowerShell разделяет сообщения по потокам:

| Поток | Команда | Для чего |
|---|---|---|
| Success (1) | Write-Output или обычное выражение | данные функции/pipeline |
| Error (2) | Write-Error | ошибки |
| Warning (3) | Write-Warning | предупреждения |
| Verbose (4) | Write-Verbose | подробная диагностика, включаемая -Verbose |
| Debug (5) | Write-Debug | отладочные сообщения |
| Information (6) | Write-Information | информационные сообщения |
| Host | Write-Host | отображение для человека; с PowerShell 5 использует Information stream |

~~~powershell
Write-Output 'data'
Write-Warning 'check this'
Write-Verbose 'details' -Verbose
Write-Debug 'debug details' -Debug
~~~

Перенаправление:

~~~powershell
.\Script.ps1 > .\output.txt       # success output
.\Script.ps1 2> .\errors.txt      # error stream
.\Script.ps1 *> .\all-streams.txt # все перенаправляемые потоки
~~~

### Терминирующие и незавершающие ошибки

- **Terminating error** останавливает текущую операцию и может быть перехвачена catch.
- **Non-terminating error** записывается в Error stream, но команда/сценарий может продолжить работу.

~~~powershell
try {
    Get-Item C:\NoSuchFile.txt -ErrorAction Stop
}
catch [System.Management.Automation.ItemNotFoundException] {
    'File was not found'
}
~~~

Основные ErrorAction:

| Значение | Поведение |
|---|---|
| Continue | показать ошибку и продолжить; обычное значение |
| Stop | превратить незавершающую ошибку в перехватываемую terminating error |
| SilentlyContinue | не показать ошибку, продолжить |
| Ignore | продолжить и не добавлять ошибку в $Error |
| Inquire | спросить пользователя |

Не используйте catch без сохранения контекста. Полезный шаблон:

~~~powershell
catch {
    Write-Error (
        "Operation failed. Type={0}; Message={1}; Position={2}" -f
        $_.Exception.GetType().FullName,
        $_.Exception.Message,
        $_.InvocationInfo.PositionMessage
    )
    throw
}
~~~

Повторный throw сообщает вызывающему коду, что операция всё-таки завершилась неуспешно.

### try/finally для освобождения ресурсов

finally выполняется и при успехе, и при ошибке:

~~~powershell
$session = $null
try {
    $session = New-PSSession -ComputerName 'server01' -ErrorAction Stop
    Invoke-Command -Session $session -ScriptBlock { Get-Service }
}
finally {
    if ($null -ne $session) {
        Remove-PSSession -Session $session
    }
}
~~~

## 9. Демонстрации циклов из курса

Последовательность чисел:

~~~powershell
for ($number = 0; $number -le 25; $number++) {
    Write-Output "Number is $number"
}
~~~

Постепенное наращивание строки:

~~~powershell
for ($characters = ''; $characters.Length -le 15; $characters += '5') {
    Write-Host $characters
    Start-Sleep -Milliseconds 100
}
~~~

Реальный шаблон массовой операции лучше снабдить ShouldProcess, логированием и обработкой ошибок:

~~~powershell
[CmdletBinding(SupportsShouldProcess)]
param(
    [Parameter(Mandatory)]
    [string]$ComputerListPath
)

$computers = Import-Csv -LiteralPath $ComputerListPath

foreach ($computer in $computers) {
    try {
        if ($PSCmdlet.ShouldProcess($computer.Name, 'Run remote audit')) {
            Invoke-Command -ComputerName $computer.Name -ScriptBlock {
                Get-Service | Where-Object Status -EQ 'Running'
            } -ErrorAction Stop
        }
    }
    catch {
        Write-Warning "[$($computer.Name)] $($_.Exception.Message)"
    }
}
~~~

Сначала запускайте с -WhatIf, если команда его поддерживает.

## 10. Безопасность PowerShell

### Принцип наименьших привилегий

- обычным пользователям не нужны Global Admin/Domain Admin;
- административная и повседневная учётные записи должны быть разделены;
- права выдаются через корректно спроектированные группы;
- скриптам и автоматизации назначаются только необходимые разрешения;
- изменение привилегий должно журналироваться и проверяться.

### Windows Features

На Windows Server модуль ServerManager предоставляет:

~~~powershell
Get-WindowsFeature
Install-WindowsFeature -Name Web-Server -WhatIf
Uninstall-WindowsFeature -Name Web-Server -WhatIf
~~~

Эти командлеты не являются универсальным способом управления ролями пользователей: они устанавливают и удаляют роли/компоненты **Windows Server**.

### Подпись сценариев

Общий процесс:

~~~powershell
# Найти сертификат подписи кода в личном хранилище
$certificate = Get-ChildItem Cert:\CurrentUser\My -CodeSigningCert |
    Select-Object -First 1

# Подписать сценарий
Set-AuthenticodeSignature -FilePath .\Script.ps1 -Certificate $certificate

# Проверить подпись
Get-AuthenticodeSignature .\Script.ps1
~~~

Для организации нужен корректно выпущенный и доверенный сертификат, защищённый закрытый ключ, управление сроками и отзывом. Одна подпись не доказывает безопасность кода — она подтверждает автора и целостность после подписания.

### Constrained Language Mode

Проверка текущего режима:

~~~powershell
$ExecutionContext.SessionState.LanguageMode
~~~

Constrained Language Mode эффективен как часть системной политики контроля приложений (WDAC/AppLocker), а не как вручную выставленная переменная внутри потенциально враждебной сессии.

### Дополнительное усиление

- Windows Defender Application Control/AppLocker;
- Script Block Logging, Module Logging, Transcription;
- AMSI и актуальная защита конечных точек;
- Just Enough Administration (JEA);
- PowerShell Remoting только по защищённым административным маршрутам;
- запрет PowerShell v2;
- централизованный сбор событий и оповещения о подозрительных командах.

Проверка PowerShell v2 на современных Windows:

~~~powershell
Get-WindowsOptionalFeature -Online -FeatureName MicrosoftWindowsPowerShellV2Root
~~~

Изменения защитных политик нужно планировать и тестировать централизованно; одиночный сценарий не заменяет GPO/MDM/WDAC.

## 12. Red Team: роль PowerShell

Курс даёт только обзор:

- PowerShell широко используется после первоначального доступа;
- цель атакующего — разведка, выполнение кода, повышение привилегий, перемещение по сети и извлечение данных;
- упоминаются PowerShell Empire и PowerSploit как исторически известные наборы post-exploitation/penetration-testing инструментов;
- те же возможности делают журналирование и ограничение PowerShell важными для Blue Team.

Практический вывод для защиты:

- отслеживать запуск PowerShell с необычными аргументами, encoded commands и обходами политик;
- анализировать Script Block Logging и связи «родительский процесс → PowerShell → сеть/дочерний процесс»;
- ограничивать привилегии, исходящие соединения и удалённое администрирование;
- использовать allowlisting, JEA, EDR и централизованный SIEM;
- проводить offensive-тесты только в лаборатории или в явно согласованном scope.

Курс не обучает полноценной эксплуатации; это обзор рисков и названий инструментов.

## 13. REST API из PowerShell

Основные HTTP-методы:

- GET — получить ресурс;
- POST — создать ресурс или запустить операцию;
- PUT — полностью заменить ресурс;
- PATCH — частично изменить ресурс;
- DELETE — удалить ресурс.

Точная семантика определяется документацией конкретного API.

### Простой GET

~~~powershell
$uri = 'https://api.github.com/repos/PowerShell/PowerShell'
$headers = @{ Accept = 'application/vnd.github+json' }

$repository = Invoke-RestMethod -Method Get -Uri $uri -Headers $headers
$repository | Select-Object full_name, stargazers_count, open_issues_count
~~~

Что здесь происходит:

- $uri хранит endpoint — адрес конкретного ресурса API;
- $headers — hashtable HTTP-заголовков;
- -Method Get явно выбирает HTTP GET;
- Invoke-RestMethod получает JSON и преобразует его в PowerShell-объект;
- через точку можно обратиться к полю ответа: $repository.full_name.

В курсе используется numbersapi.com с числом в пути и без аутентификации:

~~~powershell
$number = 42
Invoke-RestMethod -Method Get -Uri "http://numbersapi.com/$number"
~~~

Для реальной работы выбирайте HTTPS API; не передавайте токены по HTTP.

Обычный HTTP/HTTPS-запрос не требует запуска PowerShell от администратора. Повышение прав нужно только тогда, когда конкретная локальная операция действительно его требует.

В уроке переменная создаётся через Set-Variable:

~~~powershell
Set-Variable -Name number -Value 3
$number
Get-Variable -Name number
Remove-Variable -Name number
~~~

Для обычного сценария присваивание короче и понятнее:

~~~powershell
$number = 3
~~~

Set-Variable полезен, когда имя переменной формируется динамически или требуется задать scope/option, но это редкий случай.

### POST JSON и splatting

~~~powershell
$body = @{
    meal = 'pizza'
    cook = 'Barbara'
}

$parameters = @{
    Method      = 'Post'
    Uri         = 'https://api.example.test/meals'
    ContentType = 'application/json'
    Body        = $body | ConvertTo-Json -Depth 5
    ErrorAction = 'Stop'
}

try {
    $response = Invoke-RestMethod @parameters
    $response
}
catch {
    Write-Error "API request failed: $($_.Exception.Message)"
}
~~~

@{ ... } создаёт **hashtable**, а не JSON. В JSON её превращает ConvertTo-Json. @parameters — splatting: ключи hashtable становятся именованными параметрами команды.

Посмотреть JSON перед отправкой:

~~~powershell
$json = $body | ConvertTo-Json -Depth 5
$json
~~~

Обратное преобразование:

~~~powershell
$object = '{"name":"server01","online":true}' | ConvertFrom-Json
$object.name
$object.online
~~~

Depth нужен для вложенных структур:

~~~powershell
$body = @{
    computer = @{
        name = 'server01'
        tags = @('prod', 'windows')
    }
}

$body | ConvertTo-Json -Depth 5
~~~

### Заголовки и токены

~~~powershell
$token = $env:MY_API_TOKEN
if ([string]::IsNullOrWhiteSpace($token)) {
    throw 'MY_API_TOKEN is not set.'
}

$headers = @{
    Authorization = "Bearer $token"
    Accept        = 'application/json'
}

Invoke-RestMethod -Method Get -Uri 'https://api.example.test/items' -Headers $headers
~~~

Заголовки передаются как hashtable — преобразовывать их в JSON не нужно. Не храните токены и пароли в .ps1, Git или истории терминала. Используйте SecretManagement, хранилище секретов CI/CD или утверждённый организацией vault.

Параметр Credential — не то же самое, что Bearer token. Способ аутентификации задаёт документация API. Частые варианты:

- Authorization: Bearer TOKEN;
- API key в заголовке;
- Basic authentication;
- OAuth 2.0;
- client certificate;
- managed identity в облачной среде.

### Status code, pagination и ошибки

API может вернуть 2xx при успехе, 4xx при проблеме запроса/прав и 5xx при серверной ошибке. Конкретное значение нужно обрабатывать согласно документации.

~~~powershell
try {
    $response = Invoke-RestMethod @parameters
}
catch {
    $statusCode = $_.Exception.Response.StatusCode.value__
    Write-Error "HTTP $statusCode — $($_.Exception.Message)"
}
~~~

Многие API возвращают данные страницами. Нужно читать next link/token или увеличивать номер страницы до конца:

~~~powershell
$page = 1
$allItems = @()

do {
    $response = Invoke-RestMethod -Uri "https://api.example.test/items?page=$page"
    $allItems += $response.items
    $page++
} while ($response.items.Count -gt 0)
~~~

Для больших наборов $allItems += ... может быть неэффективно; лучше выдавать объекты в pipeline или использовать generic list.

Не отключайте проверку TLS-сертификата ради удобства. Таймаут и повторные попытки должны быть ограниченными, а POST/DELETE нельзя автоматически повторять, если операция неидемпотентна.

### Invoke-RestMethod и Invoke-WebRequest

- Invoke-RestMethod удобен для JSON/XML API и обычно сразу преобразует ответ в объекты.
- Invoke-WebRequest возвращает более общий HTTP-ответ и удобен, когда важны headers, status, HTML или файл.

~~~powershell
$response = Invoke-WebRequest -Uri 'https://example.com' -Method Head
$response.StatusCode
$response.Headers
~~~

## 14. Виртуальные ноутбуки

Ноутбук хранит код, Markdown-пояснения и результаты выполнения в одном документе.

В курсе показана установка VS Code extension **.NET Interactive Notebooks**, выбор PowerShell как языка, создание файла .dib или .ipynb, добавление code/Markdown cells и выполнение ячеек кнопкой Run. В качестве ежедневного security-runbook предлагаются проверка портов и запрос API уязвимостей.

Актуальность: впоследствии extension был переименован в **Polyglot Notebooks**, а его VS Code-версия была снята с поддержки 27 марта 2026 г. Поэтому инструкцию курса с .NET 6 и старым extension нельзя использовать как текущую пошаговую установку. Для нового рабочего процесса выбирайте поддерживаемый вашей организацией notebook-инструмент либо обычные .ps1/.psm1 с Markdown-документацией.

Подход полезен для:

- пошагового расследования инцидента;
- воспроизводимого security-аудита;
- демонстрации API и визуализации результата;
- учебных материалов и runbook;
- фиксации предположений рядом с кодом.

Ограничения:

- ячейки могут выполняться не по порядку, поэтому результат зависит от скрытого состояния;
- вывод может содержать токены, персональные данные или внутренние адреса;
- ноутбук нельзя считать безопасным только потому, что код разбит на ячейки;
- перед публикацией очистите output, секреты и чувствительные метаданные;
- итоговую автоматизацию лучше вынести в функции, модуль и тестируемый .ps1/.psm1.

## 15. Вопросы для собеседования

Краткие ответы на темы, которые стоит уметь объяснить:

1. **Что такое PowerShell?** Объектно-ориентированная оболочка и язык автоматизации на .NET.
2. **Что такое cmdlet?** Небольшая команда вида Verb-Noun, принимающая параметры и возвращающая объекты.
3. **Чем PowerShell отличается от CMD/Bash?** Главная особенность — объектный конвейер; PowerShell также тесно интегрирован с .NET и Windows management stack.
4. **Что такое pipeline?** Передача объектов из одной команды в следующую через |.
5. **Что такое alias?** Короткое имя команды; удобно интерактивно, нежелательно в production-скриптах.
6. **Как получить справку?** Get-Help, Get-Command, Get-Member.
7. **Как запускать сценарий?** .\Script.ps1 или оператор вызова & с полным путём, с учётом политики и прав.
8. **Что такое Execution Policy?** Механизм предотвращения случайного запуска; не граница безопасности.
9. **Как обрабатываются ошибки?** try/catch/finally; для незавершающих ошибок — -ErrorAction Stop.
10. **Разница между Write-Host и pipeline output?** Write-Host рисует интерфейс, обычный output можно передавать, фильтровать, сохранять и тестировать.
11. **Что такое splatting?** Передача набора параметров из hashtable: Command @params.
12. **Как безопасно работать с секретами?** Не хранить в коде; использовать vault/SecretManagement/managed identity и минимальные права.
13. **Как отлаживать?** Breakpoints, step execution, call stack, просмотр переменных, verbose/debug streams, Pester и PSScriptAnalyzer.
14. **Как сделать функцию пригодной для pipeline?** CmdletBinding, ValueFromPipeline, блок process, возврат объектов.
15. **Как безопасно выполнять массовые изменения?** -WhatIf, -Confirm, пилотный scope, логирование, обработка ошибок, план отката и минимальные права.

## 17. Итоговый практический шаблон

Этот каркас объединяет параметры, проверку входа, verbose-вывод, обработку ошибок, объекты и безопасный dry run:

~~~powershell
[CmdletBinding(SupportsShouldProcess)]
param(
    [Parameter(Mandatory)]
    [ValidateScript({ Test-Path -LiteralPath $_ -PathType Leaf })]
    [string]$ComputerListPath,

    [ValidateRange(1, 10)]
    [int]$Count = 1
)

Set-StrictMode -Version Latest
$ErrorActionPreference = 'Stop'

try {
    $computers = Get-Content -LiteralPath $ComputerListPath |
        Where-Object { -not [string]::IsNullOrWhiteSpace($_) } |
        Sort-Object -Unique

    foreach ($computer in $computers) {
        if ($PSCmdlet.ShouldProcess($computer, 'Test connectivity')) {
            Write-Verbose "Checking $computer"

            $online = Test-Connection -ComputerName $computer -Count $Count -Quiet -ErrorAction Stop

            [pscustomobject]@{
                ComputerName = $computer
                Online       = $online
                CheckedAt    = Get-Date
            }
        }
    }
}
catch {
    Write-Error "Audit failed: $($_.Exception.Message)"
    throw
}
~~~

Пример безопасной проверки:

~~~powershell
.\Audit-Hosts.ps1 -ComputerListPath .\hosts.txt -Verbose -WhatIf
~~~

## 18. Что в курсе стоит поправить

Самые важные уточнения к формулировкам преподавателя:

- переменные $name — это **переменные**, а не «pipe variables»;
- строки сценария не передаются автоматически по pipeline: pipeline возникает только при явном |;
- ping в Windows обычно ping.exe; объектный командлет — Test-Connection;
- aliases полезны в консоли, но для обучающих и production-скриптов лучше полные имена;
- Set-ExecutionPolicy RemoteSigned не требует scope LocalMachine; чаще достаточно CurrentUser;
- Execution Policy не является security boundary;
- постоянный запуск PowerShell от администратора не является нормой — повышайте права только для конкретной операции;
- сетевой REST-запрос сам по себе не требует прав администратора;
- catch не ловит все незавершающие ошибки без -ErrorAction Stop;
- continue пропускает итерацию, а не просто «противоположен break»;
- HTTP PUT обычно заменяет ресурс, а частичное изменение чаще выполняет PATCH;
- @{ } — hashtable, не JSON; JSON создаёт ConvertTo-Json;
- headers для Invoke-RestMethod обычно остаются hashtable и не должны содержать пароль в открытом виде;
- в PowerShell семь значений Execution Policy, а Undefined в отдельном scope не является проблемой само по себе;
- UAC и Execution Policy — разные механизмы;
- показанный extension .NET Interactive/Polyglot Notebooks для VS Code снят с поддержки в 2026 году;
- PowerShell Empire/PowerSploit следует изучать только в разрешённой лаборатории; для современной защиты важнее telemetry, allowlisting, JEA и минимальные права.

- [ ] Источник и автор проверены.
